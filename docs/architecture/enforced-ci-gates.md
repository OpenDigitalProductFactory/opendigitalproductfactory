# Enforced CI gates — trigger + trailer mechanics

The full mechanics of DPF's surface-agnostic enforced CI gates, relocated out of the always-on `AGENTS.md` preamble (BI-0020D511 instruction-plane split, §4b / §6). AGENTS.md §6 keeps the gate names, required attestation trailers, and the load-bearing rule that each gate **self-enforces in CI** (a missing trailer fails the PR, not the agent's memory); this file carries the per-gate detail an agent fetches when authoring the specific change.

All gates are surface-agnostic across Claude Code, Codex, Grok, and Build Studio because every change lands via PR (AGENTS.md §4) and each gate reads the evidence, not which surface produced it (§17, `governance-approves-evidence-not-provenance`).

- **Spec/Plan/Doc Gate (mandatory, enforced).** Specs, plans, and documentation are intrinsic platform resources, not optional follow-ups (§10). A PR that lands a substantial implementation surface — a new source module/route/migration, or a large in-place rewrite — MUST also touch a durable-knowledge artifact (a spec, plan, doc, `AGENTS.md`, a kernel principle, or a `SKILL.md`) **or** carry a `Process-Spine-Decision:` attestation trailer (in a commit message or the PR body) explaining why none is needed. This is **enforced in CI** by the `Spec/Plan/Doc Gate` check (`scripts/check-spec-plan-doc.mjs`), surface-agnostic across Claude Code, Codex, Grok, and Build Studio because all changes land via PR (§4) and the gate reads the evidence, not which surface produced it (§17 governance-approves-evidence-not-provenance). It exists because the discipline lived only in advisory skills (`dpf-writing-plans`, `dpf-architecture-review`) and prose, so external clients shipped capabilities with no spec/plan/doc — the harness-level fix for the memory-level gap diagnosed in [`docs/superpowers/specs/2026-05-30-development-process-spine-design.md`](../superpowers/specs/2026-05-30-development-process-spine-design.md) §5.2. Authoring the spec/plan is the intended path (`dpf-writing-plans`); the attestation is only for genuinely trivial changes.
- **Design Grounding Gate (mandatory, enforced for UX/workflow surfaces).** Before changing a UX, workflow, queue, navigation, attention, or process-spine surface, ground the work in the existing platform design: search the current specs/plans, inspect the code graph or `rg` substrate, name the source of truth, and state whether you are extending an existing artifact, updating it, creating a new one, or making a trivial no-contract-change edit. PRs touching these surfaces must carry a `## Design grounding` section or `Design-Grounding-Decision:` attestation that names both the specs/plans reviewed and the code substrate reviewed. The `Design Grounding Gate` (`scripts/check-design-grounding-decision.mjs`) enforces this, while the plugin pre-edit hook (`packages/dpf-skill-pack/hooks/design-grounding-precheck.mjs`) nudges fresh threads before code is written. This prevents queue/IA/UX behavior from being invented from local impressions when an approved spec or existing projector already owns the concept. On failure the gate names **exactly which of `{marker, spec-evidence, code-evidence}`** is unmet with a ✓/✗ breakdown and an accepted example, rather than one opaque "missing evidence" verdict. Code-evidence accepts the literal `code substrate`, an `apps/web/…` path, any `packages/<x>/…` path, or "mcp pack(s)"; spec-evidence accepts the literal `specs/plans reviewed` or a `docs/superpowers/(specs|plans)/…` path. For a genuinely localized edit, the **trivial no-contract-change path** — `Design-Grounding-Decision: no-contract-change (<reason of 20+ chars>)` — passes on the marker plus a reason alone, no spec/code tokens required. Put the attestation in a **commit message or the PR body**, not only in a changed doc: the gate reads doc evidence from the `base...HEAD` diff, so a doc-only attestation stops counting once `main` absorbs that doc — the gate now warns when that is the sole source.
- **Doc Reference Integrity Gate (mandatory, enforced).** The Spec/Plan/Doc Gate proves a doc was *touched*; this proves docs are not *broken*. Doc breakage is **non-local** — a route or file renamed on one side leaves a dead reference in a doc elsewhere that the PR never touched — so the gate scans the whole **live-doc corpus** (excluding `docs/superpowers/` as a source: frozen history) against the current `route-manifest.json`, not just the diff. Because `audit-route-manifest.yml` keeps the manifest fresh on every PR, a renamed route shows up as gone and every doc still pointing at it becomes newly-broken — that is the manifest-diff trigger, achieved by construction. **Enforced in CI** by the `Doc Reference Integrity` check (`scripts/check-doc-reference-integrity.mjs`), ratcheted against `scripts/docs-reference-baseline.txt` so only **net-new** breakage fails; pre-existing debt is grandfathered and can only shrink (`--update` retightens). It does **not** catch *semantic* staleness (a link that resolves but describes changed behaviour) — that is the doc-staleness attention source (BI-AA5DFEA2). EP-1155CEF3 / BI-62430075.
- **Docs Link Integrity (mandatory, enforced — EP-DOCS-SYSTEM).** The `docs/user-guide/**` corpus is rendered by two engines — the public Jekyll site and the in-portal Next.js renderer — so every internal link must resolve on **both**. Author internal links as **source-relative markdown paths ending in `.md`** (with an optional `#anchor`), e.g. `../ai-workforce/index.md#model-routing` — never an extension-less slug (`developer-setup`), never a site-absolute URL (`/user-guide/...`, `/docs/...`), never a bare directory (`getting-started/`). Surface URLs are *generated outputs*, not hand-authored. Link to a page outside the published site (a spec under `docs/superpowers/`, `CONTRIBUTING.md`) with a full GitHub URL. Both surfaces derive URLs from one resolver (`apps/web/lib/docs/doc-link-resolver.mjs`); the `Docs Link Integrity` CI check (`scripts/check-doc-links.mjs`, run via `pnpm check:doc-links`) validates every link/image/anchor against the generated `doc-index.generated.json` and **runs on docs-only PRs too** (they no longer skip scrutiny). Regenerate the index with `pnpm docs:index` when you add/rename/delete a page; normalize legacy links with `pnpm docs:links:fix`. Diagrams: author ` ```mermaid ` fences and render them to committed static SVGs with `pnpm docs:diagrams` (build-time, no client runtime; needs a compile-ready env with chromium — the `Docs Link Integrity` job enforces `--check` freshness). Screenshots/images: put them under `docs/user-guide/assets/<page-slug>/` and reference them with a relative markdown image whose src is the repo-relative path to the committed file (e.g. `../assets/getting-started/setup.png`); the resolver serves them via `/api/docs-asset` in the portal and as static files on the public site, and the link checker validates the referenced file exists. Spec: [`docs/superpowers/specs/2026-07-16-documentation-system-design.md`](../superpowers/specs/2026-07-16-documentation-system-design.md).
- **Docs Impact Gate (mandatory, enforced — EP-DOCS-SYSTEM Phase 3).** When a PR changes a **user-facing route whose page is documented** (mapped via `DOCS_ROUTE_MAP` in `apps/web/lib/docs-route-map.ts`), it must **either** update the linked `docs/user-guide/**` page(s) **or** carry a `Docs-Impact-Decision:` trailer (in a commit message or the PR body) stating why the docs don't change — e.g. `Docs-Impact-Decision: internal refactor of /finance/invoices, no user-visible change`. This ties a *specific* route change to its *specific* user-guide page, where the Spec/Plan/Doc gate is satisfied by any `docs/**` edit. Enforced in CI by the `Docs Impact Gate` check (`scripts/check-docs-impact.mjs`), surface-agnostic across Claude Code / Codex / Grok / Build Studio (it reads the evidence, not the surface — §17). The dormant `documentation-specialist` coworker (AGT-904) is the executor that repairs flagged pages. Spec §5.4. **Beyond route files, a page can declare `relatedCode:` (and `relatedRoutes:`) frontmatter listing the source files whose change should flag it — so a *functionality* change (not just a route-file edit) is caught.** These edges live in the generated doc-impact graph (`pnpm docs:impact:graph` → `apps/web/lib/docs/doc-impact.generated.json`; CI enforces `--check` freshness and that every `relatedCode` path exists). Add a `relatedCode:` list to a page when a specific module drives behavior the page documents (Phase 4, spec §5.5). **Frontmatter edges are collected from the whole published doc corpus** — every page the public site serves, derived from `docs/_config.yml`'s own `exclude:` list via `scripts/lib/published-doc-roots.mjs`, not just `docs/user-guide/**`. The earlier user-guide-only walk was a blast-radius hole: `docs/architecture/**` and `docs/operations/**` are published at `opendigitalproductfactory.com` and are exactly where runtime-topology and incident-recovery pages live, so a change could retire a whole datastore with no gate flagging the pages that described it (BET-5 Neo4j/Qdrant → `/architecture/platform-overview/` and the DR runbook). Edges remain opt-in, so widening the corpus adds no noise until a page declares them — but **a page that names specific services, schemas, or scripts should declare them.** **Dependency-manifest-only exemption:** a diff whose *entire* file set is dependency manifests/lockfiles (`package.json`, `pnpm-lock.yaml`, `pnpm-workspace.yaml`, `package-lock.json`, `yarn.lock`, `npm-shrinkwrap.json`) is skipped (`isDependencyOnlyChange`), because it carries no source or user-guide file for a *docs* gate to enforce. Without it, a doc that cites `pnpm-lock.yaml`/`package.json` (a `relatedCode` edge) flagged **every** dependency bump as impacting and demanded a trailer — which a bot author like **Dependabot cannot add**, structurally wedging every bump PR (#4184–4188). The exemption reads the file set, not the author, so it is surface-agnostic and **cannot smuggle a source or doc edit past the gate**: a single non-manifest file makes the set non-manifest and the gate runs in full. Manifest content is still gated by build-script policy, lockfile release-age, and the OSV scan.
- **Retired Substrate Guard (mandatory, enforced).** The Docs Impact Gate above proves a *change* reached its documented page; this proves the published corpus does not still **name infrastructure the platform no longer runs**. It is the complement the doc-impact graph cannot be: those `relatedCode:` edges are **opt-in**, so they protect only pages someone remembered to annotate — the same "someone must remember" failure that let BET-5 retire Neo4j and Qdrant while `/architecture/platform-overview/` kept presenting Neo4j as a live datastore and the disaster-recovery runbook kept telling operators, mid-incident, to run `restore-neo4j.sh` and `docker compose up -d postgres neo4j qdrant` against decommissioned containers. This guard needs no cooperation from the page; it reads the words that are actually published. Retired terms live in `scripts/retired-substrate.json` (term + what retired it + what replaced it); every live doc mentioning one must appear in `scripts/retired-substrate-baseline.txt`, ratcheted exactly like the Doc Reference Integrity baseline — grandfathered mentions may only shrink, and a **net-new (page, term) pair fails**. It deliberately **scans fenced code blocks**, because the most dangerous real instance was a copy-pasteable command in an incident runbook. **Retiring something new is one line in the registry**, after which every stale page surfaces at once — `pnpm check:retired-substrate` to see them, `pnpm check:retired-substrate:update` to baseline the ones that are genuinely historical context. Enforced in CI by the `Retired Substrate Guard` check (`scripts/check-retired-substrate.mjs`). Do **not** baseline a mention you cannot honestly call history — a live instruction pointing at a dead service is a defect, not debt.
- **Data-Impact Gate (content-based — BI-DG-003, EP-DATA-GOVERNANCE).** A PR that changes a **persistent surface** — a Prisma model/field, migration, projection producer, AI-context source, MDM domain, or lifecycle executor — must carry a generated `*.data-impact.json` manifest describing the affected logical assets (change kinds, per-field resolution `inherited|governed|not-applicable` with reason + provenance, governed field policy for sensitive/subject/prohibited fields, derived-copy contracts + cleanup/reconciliation for new projections, hold-check + disposition evidence on destructive paths, and policy test vectors) — **or** a structured `*.data-impact-exception.json` (scope, approver, rationale, compensating control, expiry, remediation BI). An exception may cover a temporary gap but can **never** waive asset/lifecycle coverage for a new persistent model or permit prohibited storage. Not a "file touched" check: enforced in CI by the `Data-Impact Gate` check (`scripts/check-data-impact.mjs`) over the changed surfaces. Pre-existing gaps live in the immutable BI-DG-002 legacy baseline (`apps/web/lib/govern/data/legacy-coverage-baseline.ts`); this gate holds the line on new changes. Design: spec `docs/superpowers/specs/2026-07-17-data-management-governance-design.md` §6.9.
- **Convergence-Impact Gate (mandatory, enforced — BI-B19BE117).** The sibling of Data-Impact for every non-data surface that reaches an **existing install** only through some convergence mechanism, or not at all. Deployments are cumulative: any install may upgrade from any past version, so each increment has to state how it converges — today that lives in release notes and human memory, and it keeps surfacing as individual defects (BI-3727106F hook convergence was install-time only; BI-BE8BBDE9 existing installs could not self-upgrade into the install-state migration; BI-922EBB99 retired datastores left orphaned; #3262 a compose var never provisioned). When a PR changes a registered surface — compose / Dockerfile / entrypoint, `.env*.example`, installer / launcher / promoter / `scripts/installer/**`, `.githooks/**` + hook convergers, `config/**`, a file the portal `Dockerfile` COPYs **by name** (parsed live, single-file sources only), or canonical seed content (the same `config/seed-content-paths.json` the Seed-Fit gate reads) — it must carry `Convergence-Impact-Decision: <mode> — <mechanism or reason, 20+ chars>` in a commit message or the PR body. Modes are closed: `auto-converges` (name the mechanism: promoter compose-from-release, session-start hook converger, seed re-run, install-state migration edge …), `self-upgrade-step` (this PR adds the step), `operator-action` (name the action and the runbook), `fresh-install-only` (older installs do not need it — say why), `not-reachable` (classifier false positive — say why, so the registry can be tightened). Tests, fixtures and app source under `apps/` / `packages/` never classify (data surfaces belong to Data-Impact; behaviour converges by image rebuild). Registry with a cited `why` per surface: `scripts/convergence-surfaces.json`. Enforced in CI by the `Convergence-Impact Gate` check (`scripts/check-convergence-impact.mjs`, `pnpm check:convergence-impact`); advertised before generation by `gate-context.mjs`. It records the claim; it does not verify it — that is the N-1 acceptance run and the coworker reading the trailer later. Kernel decisions `DI-9DF1A83ECACD` (blocking with a narrow classifier, not shadow) and `DI-91594F6EF8FA` (sibling, not folded into Data-Impact). Design: `docs/superpowers/specs/2026-09-06-convergence-impact-gate-design.md`.
- **Stewardship Scope Guard (BI-C34E09B0).** Adding a **persistent Prisma model** also widens stewardship scope, so the model must declare **both** (1) a sensitivity in `packages/db/src/table-classification.ts` and (2) exactly **one** retention disposition: a `PURGE_POLICIES` entry, a `RETAINED_DATASETS` entry with a cited regulatory basis (both `apps/web/lib/operate/retention/policies.ts`), or a typed line in `scripts/stewardship-exemptions.txt` (`reference-data | config-singleton | domain-lifecycle-managed | derived-projection`). Absence is not a decision: unclassified falls through to `DEFAULT_SENSITIVITY = "confidential"` — a guess presented as a decision — and an un-dispositioned model is never swept, forever, silently. Enforced by the `Stewardship Scope Guard` CI check (`scripts/check-stewardship-scope.mjs`). Integrity errors (dangling registry entry, unknown exemption reason, two dispositions) **never** grandfather; pre-existing coverage gaps ratchet down from `scripts/stewardship-scope-baseline.txt` and a new model must **never** be parked there. **Do not invent a purge window to clear the gate** — the retention engine *executes* `PURGE_POLICIES`, so a fabricated window on reference data deletes it; declare an exemption instead. Kernel decision `DI-F10DB4681452`.
