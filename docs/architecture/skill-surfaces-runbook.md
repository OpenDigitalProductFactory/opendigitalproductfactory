# Skill surfaces runbook

**Status:** procedure reference. The *precedence and routing rules* live in [`AGENTS.md`](../../AGENTS.md) §16 and stay always-on — they govern behaviour before an agent would know to fetch an index. This file holds the authoring/seeding mechanics, the process-spine health-check contract, and the `principle_decide` call detail. Relocated from §16 by BI-0020D511 Phase 1; no rule was dropped.

- **Dual-surface contract.** DPF platform skills are authored once in superset `SKILL.md` format at `packages/dpf-skill-pack/skills/<slug>/SKILL.md`. Claude Code and Codex load those files through the checked-in `dpf-platform` plugin marketplaces; the plugin is also the home for client MCP descriptors, the governance hooks (`packages/dpf-skill-pack/hooks/` → `hooks/hooks.json`, shipped to all three surfaces per BI-CA0ED781), and runtime assets. `packages/db/src/seed-skills.ts` seeds the same files as `SkillDefinition` + `SkillAssignment` rows for in-portal coworkers. Both surfaces converge on the same body and kernel-principle enforcement.
- **Generic skills (Surface A only).** Non-DPF skill packs are not project-default development precedent. Use `dpf-platform` first; install upstream generic packs only in local/user scope for a documented task gap, and promote recurring value into this DPF plugin before treating it as standard practice. Never seed generic packs for in-portal coworkers.
- **Process-spine health check.** The canonical retired-to-DPF replacement map and cleanup/update lifecycle policy live at `packages/dpf-skill-pack/process-spine-replacements.json`; bootstrap and the plugin `SessionStart` hook run `packages/dpf-skill-pack/hooks/process-spine-health-check.mjs` against it. Readiness must report "DPF-native replacement skills installed" separately from "loaded/exposed in this session" and "cleanup/update" status. If a client exposes active skill evidence and any retired `superpowers:*` process skill is visible without its DPF replacement, treat the session as DPF-precedence-unproven and repair/restart before project work. Cleanup is disable-not-delete: safe adapters may disable known competitive plugins, but must not delete user-owned skill files or plugin caches.
- **DPF platform skill catalogue.** The full per-skill trigger / Surface-B `assignTo` / enforced-principle index lives at [`docs/architecture/agent-skill-index.md`](../architecture/agent-skill-index.md); each client's own skill system also surfaces these skills. Author new skills in `packages/dpf-skill-pack/skills/<slug>/SKILL.md` (the source of truth). The doctrine sub-rules below (precedence, process-spine health, `composesFrom` disambiguation, WWMD/WWWD routing) stay here.
- **Legacy coworker skills (Surface B only).** Existing coworker skills live at `skills/<category>/*.skill.md` and keep the older frontmatter until EP-SKILL-001 migrates them opportunistically. New DPF skills MUST use the superset format in `packages/dpf-skill-pack/`.
- **DPF spec/plan locations.** Specs live at `docs/superpowers/specs/YYYY-MM-DD-<topic>-design.md`; plans live at `docs/superpowers/plans/YYYY-MM-DD-<feature>.md`. **Artifact format is opt-in:** Markdown is the default; for specs/plans/reports/PR write-ups that carry flow diagrams, multi-column tables, or side-by-side option fan-out, an HTML artifact (same locations, `.html` extension) often reads better and keeps the operator in the loop — see [`docs/superpowers/html-artifacts-guide.md`](../superpowers/html-artifacts-guide.md), the `docs/superpowers/_templates/*.html` starters, and the worked pilot at [`docs/superpowers/specs/2026-06-09-release-verification-health-surfacing-design.html`](../superpowers/specs/2026-06-09-release-verification-health-surfacing-design.html). HTML-only artifacts should leave a short Markdown stub so `search_specs_and_plans` still indexes them. The DPF-only `/project:tool-evaluation` command remains at `.claude/commands/tool-evaluation.md` for EP-GOVERN-002 external-tool evaluation, alongside `.claude/commands/build-studio-operator.md` until a re-home BI says otherwise.
- **Disambiguation rules.** Surface A: "DPF skill wins over superpowers when both could apply". Surface B: "plugin SKILL.md wins over legacy .skill.md at seed time". **DPF-vs-DPF (intra-pack overlap):** when two DPF skills' `triggerPattern`s match the same task, resolve by (1) the `composesFrom` chain — the predecessor fires first (e.g. `dpf-evidence-before-diagnosis` before `dpf-systematic-debugging`; `dpf-brainstorming` before `dpf-decision-via-kernel`; `dpf-file-backlog-item` before `dpf-writing-plans`), then (2) the most specific `description` DPF-context selector. The chains encode intended order; a trigger overlap is not a conflict.
- **Kernel principles (Surface C).** Durable doctrine lives at `docs/founder-kernel/wiki/principles/`. Use `wiki_query` for principle lookup and `principle_decide` for scored decisions when the connector is available; `dpf-decision-via-kernel` is the procedural bridge from either runtime.
- **WWMD vs WWWD — which decision surface governs.** `dpf-decision-via-kernel` / `principle_decide` is the **platform-development (WWMD)** decision surface — for DPF contributors and Build Studio *platform* work, scored against the founder kernel. **A customer's business decision (in-portal coworker) must route through the Decision Perspective Gate against the organization's WWWD profile**, which enforces the non-inherit boundary: a customer profile does **not** inherit platform-specific business judgment as authority by default (DPF product doctrine is advisory only until the org seeds its own WWWD). The two surfaces are being consolidated so the Gate is the single governed door (BI-E1FB2307); until that lands, do not use raw `principle_decide` to settle a customer's business question. See `docs/user-guide/ai-workforce/decision-perspective.md`. The governing doctrine is the kernel principle [`decisions-belong-to-their-scope`](../founder-kernel/wiki/principles/decisions-belong-to-their-scope.md) — each decision resolves in its owning scope (WWMD/WWWD/WSID) and no scope's doctrine binds another as authority (subsidiarity).
- **Work-scope / altitude decisions are platform-owned (WWMD) — consult, don't ask cold.** How much to take on in a pass (spec-only vs spec+implementation, refactor vs special-case, which approach/architecture) is a **platform/build decision**: route it through `dpf-decision-via-kernel` / `principle_decide` **before** surfacing a menu. `consult-scopes-before-asking` is a commandment — act on a high-confidence recommendation and report the ledger; escalate to the human only on low confidence (margin < tieMargin) or a commandment conflict. "Option 1/2/3, you pick" without a ledger is the anti-pattern. **Harness-enforced** by the `decision-routing-guard` PreToolUse hook (matcher `AskUserQuestion`); because that wiring is branch-versioned, a `[governance-freshness]` SessionStart warning means treat every decision as guard-off and route it manually. Spec: [`2026-07-03-harness-enforced-decision-routing-and-lease-punt-gates-design.md`](../superpowers/specs/2026-07-03-harness-enforced-decision-routing-and-lease-punt-gates-design.md).
- **Calling `principle_decide`: supply `features`, and read `signalQuality` before `recommendation`.** `features` is schema-optional but **load-bearing**: commandments score on the structured path, so an option with no `features` scores zero against every commandment → `insufficientSignal: true`, `recommendation: null` (an abstention, not a tie). Always check `data.signalQuality.usable` before acting on `data.recommendation`; an insufficient-signal consult is the caller's defect to fix by re-calling with features, not a human review. Each feature answers **"how much does this option EXHIBIT this axis?"** — a magnitude, never a goodness rating; on the five **cost** axes (`blast_radius`, `human_cognitive_load`, `vendor_lock_in`, `business_disruption`, `operator_effort`) **higher is worse**. The closed key set travels in the tool schema (`apps/web/lib/decision/dimension-catalog.ts`); an unknown key is rejected. Bridge: `dpf-decision-via-kernel`.
- **A mandated skill is pinned, not ranked (Surface B).** Eligible skills are relevance-ranked per turn and cut to `DEFAULT_SKILL_SUMMARY_CAP` (12) in `apps/web/lib/skills/skill-relevance.ts`. The four decision skills named in `packages/db/src/mandated-skills.ts` — the WWMD/WWWD stack every persona inherits via `assignTo: ["*"]` (BI-5E8E231E) — keep a reserved slot **before** ranking; only the remaining slots are contested. Pinning **spends** slots rather than adding them, so no coworker's per-turn budget grows. Without the reservation the mandate is asserted at seed time and unenforceable at ranking time: measured across 1,175 real turns on a live install, 61.4% dropped at least one mandated skill and `dpf-decision-via-kernel` alone was dropped on 57.3% (BI-43920DD1, kernel ruling `DI-E68BCB1767BD`). Add a skill to that list only when the platform genuinely guarantees every persona inherits it — each entry is a slot taken from every coworker's own skills on every over-cap turn.
