# Backlog & planning runbook

**Status:** procedure reference. The *rules* — backlog lives in Postgres, plan before build, check epic overlap — live in [`AGENTS.md`](../../AGENTS.md) §6 and stay always-on. This file holds the tooling detail, hygiene cadence and enforced-gate list. Relocated by BI-0020D511 Phase 1; no rule was dropped.

- **Backlog lives in PostgreSQL** (`Epic`, `BacklogItem`). Always query live state before planning or changing backlog work. → [kernel principle](../professions/portfolio-management/wiki/backlog-lives-in-postgresql.md)
- **Use the DPF MCP backlog tools first when available.** Local agent clients are configured by the untracked `.mcp.json` generated from Admin > Platform Development. It points the `dpf` server at the canonical MCP endpoint `/api/mcp/v1`, which exposes backlog/planning tools such as `list_backlog_items`, `get_backlog_item`, `create_backlog_item`, `update_backlog_item_status`, `list_epics`, `link_backlog_item_to_epic`, `search_specs_and_plans`, and `record_execution_evidence` according to the caller's token scopes. `search_specs_and_plans` reads the `docs/superpowers` tree from the install root, and consumer/runtime-host images exclude that tree on purpose. Where it is absent the tool returns `spec_plan_corpus_unavailable` rather than an empty result, and `hasSpec`/`hasPlan` on the backlog read tools carry a "coverage was NOT measured" caveat — check a source checkout before treating either as evidence that no design exists.
- **DB fallback must be explicit.** If the `dpf` MCP server is unavailable in the current agent session, query the live Postgres database directly and say that you used DB fallback. Do not substitute `packages/db/src/seed.ts`, generated Prisma files, or stale docs for current backlog state. → [kernel principle](../founder-kernel/wiki/principles/db-fallback-explicit.md)
- **Replacement-install recovery is explicit, not automatic seed data.** A narrowly scoped, version-controlled recovery bundle may preserve platform-development coordination records that would otherwise be lost with an installation database. Validate and preview it first with `pnpm --filter @dpf/db backlog:reconcile -- <bundle.json>`; add `--apply` only after reviewing the stable IDs reported as missing. Apply runs in one transaction, creates missing records, and skips every existing epic or item wholesale, so it cannot regress newer status, evidence, or claims. Recovery bundles must never be imported from `packages/db/src/seed.ts`: customer installs do not inherit DPF's internal roadmap. Use the normal MCP/PostgreSQL lifecycle for current work and full database backup/restore when the whole installation—not a bounded program—must survive.
- **Capture is the other half of recovery, and it goes stale.** Every epic with a not-done item must have a *current* bundle in [`packages/db/recovery/backlog/`](../../packages/db/recovery/backlog/README.md), merged to `main` — a bundle on an unmerged branch is not a backup, and a stale bundle is worse than a missing one because the epic still looks protected while the items filed since capture are exactly the ones lost. Re-capture with `pnpm --filter @dpf/db backlog:capture -- --out packages/db/recovery/backlog` immediately before any reset or teardown, and check `manifest.json` closes: `capturedItemCount + unassignedItemCount == unfinishedItemCount`. Items with no epic cannot be bundled (the format is epic-scoped and requires `epicId`) — link them with `link_backlog_item_to_epic` first, or accept they survive only as the non-reconcilable `unassigned-items.json` record.
- **Specs and plans** live in `docs/superpowers/specs/` and `docs/superpowers/plans/`. A build-bound BI and its proportional design are one capture outcome: reuse, extend, or create the canonical design, cross-link the generated BI id, and preserve both in the same delivery PR. A source-incapable caller leaves the BI in `triaging` with an explicit design handoff; it must not present the item as build-ready. Check for an existing design before starting work — some are ready to implement.
- **Plans need live backlog coverage before implementation.** Use `dpf-writing-plans` and the governed `record_plan_backlog_coverage` receipt. Every independently shippable deliverable maps to a live new or existing `BacklogItem`; an `xlarge` BI always records a decomposition decision. Keeping one BI is allowed only with an auditable rationale that its phases are sequencing, not independent work. Copy the receipt, BI mappings, and dependencies into the plan. MCP/tool/scope failure stops the workflow — Markdown checkboxes are never backlog coverage. The plugin pre-source guard is the earliest hard boundary; the Plan Backlog Coverage CI check is the repository backstop.
- **A schema-v2 coverage receipt needs a scope baseline, and only an independent reviewer can mint one.** `record_plan_backlog_coverage` binds the plan to the umbrella item's `initiative_scope_baseline`. A baseline exists only after the initiative's spec-approval gate passes: `record_initiative_design_review` with `gate: "spec-approval"`, `decision: "pass"`, and a canonical design under `docs/superpowers/specs/` whose objectives are marked `**OBJ-*:**` and whose acceptance statements are `| AC-* | OBJ-… | statement |` table rows (the server parses the manifest; the caller never supplies it). That lane requires a reviewer **independent of the artifact author**, and independence binds between *principals*: an author cannot approve their own design, superuser status does not waive it, and there is deliberately no break-glass self-approval path — adding one needs its own design with second approval, expiry, rationale and durable audit ([initiative-readiness design](../superpowers/specs/2026-08-08-initiative-readiness-and-goal-completion-reconciliation-design.md) §361).

  **On an install with one human principal, the independent reviewer is an in-platform reviewer coworker, not another person.** A coworker has its own `Principal` (`kind: agent`) and its own `initiative_design_review` grant; summon it and have *it* record the gate, and the receipt is attributed to the coworker's principal rather than to the delegating human. Recording the same call yourself is a self-review and is refused — correctly. This is the paved road, not a workaround: the review is by a differently-grounded reviewer with its own accountable identity and its own audit trail. Before the fix, every reviewer resolved to the human regardless of who called, so no install could produce a baseline and no v2 coverage receipt existed anywhere.
- **Enforced process/docs/data CI gates (mandatory, surface-agnostic).** A substantial implementation surface needs a spec/plan/doc touch or a `Process-Spine-Decision:` trailer; a UX / workflow / queue / nav / attention surface needs a `## Design grounding` section or `Design-Grounding-Decision:` trailer naming the specs/plans AND code substrate reviewed; a documented user-facing route change needs the doc edit or a `Docs-Impact-Decision:` trailer; a persistent Prisma model / migration / projection / AI-context source needs a generated `*.data-impact.json` manifest (or exception) AND a `packages/db/src/table-classification.ts` sensitivity + exactly one retention disposition. Internal doc links are source-relative `.md` paths — regenerate with `pnpm docs:index` on add/rename/delete. **Each gate self-enforces in CI, so a missing trailer fails the PR, not your memory** — the reason this detail need not stay always-on. Full per-gate trigger + trailer mechanics (Spec/Plan/Doc, Design Grounding, Doc Reference Integrity, Docs Link, Docs Impact, Data-Impact, Stewardship Scope): [`docs/architecture/enforced-ci-gates.md`](../architecture/enforced-ci-gates.md).
- **Data classification has three orthogonal axes (BI-81ABBDA2).** Confidentiality LEVEL (`packages/db/src/table-classification.ts`: public|internal|confidential|restricted, per-MODEL) is distinct from data TYPE and from regulated SCOPE. Per-FIELD classification lives in `apps/web/lib/govern/data/field-classification.ts` (`FIELD_DATA_CLASSIFICATION`, keyed `Model.field`): `categories` reuse the existing `DataCategory` vocabulary (`govern/data/taxonomy.ts` — do NOT invent a parallel enum), and `regulatedScope` (`pci-cardholder` | `phi-health` | `none`) carries the legal regime `DataCategory` cannot express. "Which fields hold cardholder data / PHI / credentials?" is answerable by query (`fieldsHoldingCardholderData()` etc.), not by regex over prose or an org-level boolean. It is an extensible seed inventory (coverage grows like the stewardship-scope baseline); `field-classification.schema.test.ts` fails if any classified `Model.field` is not a real column, so it cannot silently drift. When conditioning governance on a data type (e.g. HITL sign-off for PCI — BI-0B4B16CA), key off this registry, never a free-text match.
- **Before creating a new epic:** query existing epics for overlap. Prefer extending an existing epic over creating a new one. If superseding an old epic, mark it done in the same operation. → [kernel principle](../professions/portfolio-management/wiki/check-epic-overlap-before-creating.md)
- **On completing items:** update status in the DB immediately. The system auto-closes epics when all items are done/deferred. Direct DB ops require manually flipping the parent epic.
- **A deferral without a reason, trigger, review date and owner is not a park — it is a disappearance.** `status="deferred"` is only half a decision: nothing fires without a trigger, nothing comes due without a review date, and nobody picks it up without an accountable owner, while the item reads as handled and drops out of every sweep that would surface it. Compose deferrals through `normalizeDeferralInput` (`apps/web/lib/backlog/deferral-contract.ts`) and spread the result, as the governed backlog action does; record a `status_change` activity on the **item**, not only on the build or job that parked it. This is enforced by the Unattributable Deferral guard (`scripts/check-no-unattributable-deferral.mjs`) because a direct Prisma write bypasses the governed tool's validation — which is exactly how build escalation parked seven items, including the one tracking the readiness deadlock, with all four fields null and no activity trail. Cleaning those rows achieves nothing while a write path keeps producing them (BI-9DA5F179). The guard also refuses a status copied through from another record (`status: item.status`) inside a BacklogItem write: that is how the same-organization work-sync mirror parked 18 items on 2026-09-02 with no literal `"deferred"` anywhere in the file. A mirrored deferral now travels with its reason, trigger and review date and is owned by the link's federated-peer Principal; an origin that shared nothing is written with that gap as the reason, never as a bare `deferred`.
- **Periodic hygiene:** epics with 0 items + status `open` are noise — add items or delete. Epics where all items are done but status is still `open` must be flipped.
- **Execution evidence is canonical-runtime evidence.** When recording build-gate, UX, or migration evidence via `record_execution_evidence` (or the Build Studio equivalent), the command + output must come from the canonical local install per §5 after the governed self-upgrade path has deployed the target, or from the shared local-CI convergence sandbox. A worktree-only "green" for a runtime-bound gate is a source-control checkpoint, not execution evidence.
- **Reviewer routes resolve only after the Workroom is bound to a branch and head SHA.** The first `claim_backlog_item_for_work` refusal on an unbound Workroom returns `escalations: [{ reason: "no-eligible-reviewer" }]` with an EMPTY `reviewerRoutes`, which reads like a dead end and is not one. Call `record_external_development_evidence` with `branchName`, `worktreePath` and a **full 40-character** `commits[0]` first — a short SHA leaves the Workroom head stale and the packet keeps citing the old commit — then re-claim. The second refusal carries resolved `reviewerRoutes` with a ready-made `requestCoworker` payload per gate. Pass that packet through verbatim: `requiredToolNames` must be the bound writer plus the immutable source readers (`read_source_at_version`, `search_source_at_version`) and nothing else, or the call is refused as `invalid_initiative_review_packet`.
- **An exact server-bound initiative-readiness receipt does not ask the business owner for a technical rubber stamp.** A validated `initiativeReviewBinding` fixes the TaskRun to one BacklogItem, immutable artifact, gate, and `record_initiative_*` writer, with exact authority scope and reviewer grants. That bounded internal receipt bypasses only the coworker's generic numeric tier/side-effect approval default; an explicit operator `hitlPolicy: "always"` still wins, and the receipt repository still enforces role eligibility, token scope, tenant scope, and author/reviewer separation. Unbound or mismatched calls and non-readiness side effects retain their normal approval or denial path. When an approval is genuinely required, treat `TaskRun.status = input-required` as the durable signal, inspect the bound `CoworkerActionEnvelope`, and do not re-fire the same `requestKey` blindly.
