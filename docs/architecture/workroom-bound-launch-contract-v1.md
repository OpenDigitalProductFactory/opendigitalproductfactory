The [approved design](../superpowers/specs/2026-11-25-workroom-bound-toolset-design.md) and [atomic activation plan](../superpowers/plans/2026-11-25-workroom-bound-toolset-plan.md) remain in force. ## Launch and custody

- `schemaVersion` must be exactly `s5-launch.v1`. The protected FB-2c launch exchange must authenticate the DPF issuer and pinned DPF2 Control receiver, and integrity-protect the entire launch object, including version, audience and every nested field. A consumer must compare issuer, audience, host, room, session, stage, attempt, mode, subject and resource to independently obtained admission and Store state. It must not use a received value to set or repair its expectation. A host mismatch, missing binding, stale attempt or unsupported version is a hold. Resume can reattach only the same admitted attempt. An exact replay may return existing facts but must not create authority or custody again.
- `subject` is the single `{ principalId, gaid }` block. `principalId` is the canonical DPF `Principal.principalId`, not the relational row ID or the receiver actor ID. `gaid` must be the unique current local GAID alias of that admitted Principal. The producer holds if the alias is missing, belongs to another Principal or is ambiguous. The receiver must refuse a changed GAID or Principal even if the message otherwise authenticates. This follows DI-9192F4CB566D. S6 owns the shared freshness epoch/floor. This contract does not add one.
- `authority` carries the current explicit binding, permit and exact grant keys, and the projection carries the current stage and attempt. These are non-secret references for validation, not grants. Compose the operation set through the existing coordinator eligibility seam from the assigned job and active GAID, stage, binding, permit, grants, applicable JSI ceiling and deployed registry. Recheck current authority before effects. The consumer can narrow but cannot add an operation.
- `bounded-coding` requires the exact admitted worktree. The launcher must intersect the operation list with its supported confined-mode operations and fail closed if it cannot enforce the exact boundary. A listed name alone cannot authorize a shell, a test outside its dedicated profile or source outside the worktree.
- Under DI-47F59A9896C6, the `dpfroom_` credential is opaque, held only by the pinned DPF2 Control receiver, and travels separately over the same secure launch exchange. The future attempt-bound broker mediates only admitted operations through a kernel facade. Do not put the token in the projection, model payload, guest, T3, logs or resume data. Missing compatible credential or unsupported enforcement holds the launch. Never fall back to the legacy write-capable `workroom_session`. Issuance, rotation and revocation are later implementation work.

## JSI decision

The authenticated launch carries `jsi`. Only `eligible` is valid for `read-only-coordination` and for the first production pilot. It carries `qualification` with the authoritative `id`, `version` and `statusRevision`, `validUntil` in Unix milliseconds, and the full selector except `subject`. Restore `subject` from the top-level block before comparing the full canonical selector with the independent expected scope. `profileFingerprint` lives only in that selector. The approved no-scheme case stays `not-applicable` for other explicitly admitted activities where the resolver establishes it. Unavailable, unknown, narrowed, suspended, incompatible or stale decisions do not produce an eligible projection.

The server must obtain this from `resolveS5JsiEligibility` through the existing coordinator eligibility seam, never from request or fixture data. The selector installation must equal the issuer and the launch window must end no later than `validUntil`. Issuance must precede expiry. Admission or resume requires current time in the launch window, before `validUntil`, and fresh verification of the exact stage attempt, binding, qualification revision and S6 floor. Re-read current scope and qualification before broker effects. A previously authenticated `eligible` payload is not proof of current qualification. The companion resolver test exercises a synthetic source only.

## Read-only coordination and the no-wake proposal

`read-only-coordination` is the mode for `s5-route-handoff`. Its ceiling is exactly the following operations. A current assignment may narrow the displayed list. There is no source worktree, source edit, test, PR, shell, dispatch, reassignment or general message capability.

| Operation | Broker ceiling |
| --- | --- |
| `get_workroom` | Read the admitted Workroom and its bounded assignment only. |
| `read_room_messages` | Read the exact admitted case only. No `unreadForMe` or other call that advances a read position. |
| `post_room_message` | Record a route proposal on that exact synthetic case for the pilot. Never call the ordinary posting path. |

For a proposal, Control passes recipient `authorityRef`, `destinationRef` and `reservationRef` as opaque, non-addressing data. The broker validates all three against the expected recipient and current records, and the `caseKey` against the admitted synthetic case, before commit. The references do not authorize spending the reservation, dispatch or launching a recipient. Inputs must have no `addressedTo`, role alias, or addressing override. The v1 proposal body refuses `@` text. No notification or external effect is allowed. The proposal path must not emit `room/message.posted`, queue a wake or result in a recipient provider turn. This invariant is independent of what the proposed text looks like.

Control generates a random `room-operation:<uuid-v4>` once per operation claim. It belongs at the top level of the authenticated `coordination-broker-call`, beside `operation` and `args`, not in the launch or model tool arguments. The broker durably binds it to the authenticated issuer, audience, host, Workroom, session, stage and exact attempt, plus the immutable call. An exact acknowledgement and exact historical readback echo that ID unchanged. An exact replay must not record a second proposal or effect. Conflicting reuse is refused. Missing or ambiguous durable proof is unknown and does not authorize resend. No portable `requestDigest`, body or content-derived commitment appears in acknowledgements or readback. See DI-2624A27F9F56 and the S6 evidence on BI-687E7D81.

## Provider metering

The launch budget caps input bytes, input tokens, output tokens and reasoning tokens per provider call. The pilot ceiling is 10,000 input tokens and 1,200 output tokens. The fixture uses a smaller explicit reasoning ceiling as an example, not an operator setting. Reasoning must fit inside the output cap. The relay can reduce those limits. It must not send if the model adapter cannot measure the real input or enforce the selected input, output and reasoning limits.

The `provider-preflight` record is bound to the same issuer, receiver, host, Workroom, session and stage attempt, plus the exact provider call, model and tokenizer. Before submitting, measure the exact serialized provider input that will be sent. Count UTF-8 bytes for prompt, provider-facing projection, room context and tool schemas. Count every remaining payload byte as framing, including escaped JSON and other model request fields that are not in those four parts. The byte parts must sum to the exact body length. The token count is for the full input with the actual provider/model tokenizer, not a sum of independently tokenized parts and not an estimate from message history. The applied limits must fit the launch budget and the dispatched input must fit the applied limits. Re-apply and re-measure if the request changes before dispatch. Record accounting outside the payload so it cannot change the input it measures. The uncapped legacy room history injector is not an S5 input path. The fixture uses a synthetic tokenizer and illustrates accounting without claiming provider enforcement.
