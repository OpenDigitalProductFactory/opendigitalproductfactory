# Tool Evaluation: Step CA v0.30.2

**Backlog item:** `BI-52D34506`
**Decision:** conditional approval
**Risk:** medium
**Confidence:** 0.88
**Re-evaluate after:** 2027-01-20, or immediately after a Step CA security advisory

Step CA is the organization-level private PKI selected for certificate-valid
HTTPS between DPF installations. It is Apache-2.0 licensed, self-hosted, and
implements standard X.509 enrollment and renewal rather than asking DPF to
implement a certificate authority. Governed decision `DI-236363AB3AA3`
recommended this option with high confidence (composite 5.319, margin 0.932).

The approved image is
`smallstep/step-ca:0.30.2@sha256:a2b17872915c193259b75a5474c398326f41bd199f0842093e52cf4182bc8270`.
Never use `latest` or a mutable version-only reference in DPF runtime files.

## CoSAI security findings

| # | Category | Severity | Finding | Required treatment |
| --- | --- | --- | --- | --- |
| 1 | Authentication | medium | JWK/ACME/SCEP provisioners are powerful certificate-issuance authorities. | Enable only provisioners used by DPF; use short-lived, one-time enrollment tokens and file-backed passwords. |
| 2 | Access control | medium | The open-source server does not provide the commercial product's fine-grained RBAC. | Keep administration inside the Authority boundary; do not expose remote management; authorize enrollment in DPF before minting a token. |
| 3 | Input validation | low | v0.30.2 contains the March 2026 SCEP validation fix. | Pin v0.30.2+ and constrain allowed SANs/lifetimes in provisioner policy. |
| 4 | Data/control boundary | low | Step CA signs CSRs; it does not consume prompts or business data. | Pass only certificate identity, SANs, and lifecycle metadata. |
| 5 | Data protection | medium | The root/intermediate keys and provisioner password are installation-wide secrets. | Store keys in a dedicated volume, password in a mode-0600 file-backed secret, never environment variables or logs; document backup/recovery. |
| 6 | Integrity controls | low | Official multi-architecture image publishes immutable digests. | Pin the evaluated digest and retain repository secret/image scanning. |
| 7 | Session/transport | low | The CA API is TLS-protected and clients bootstrap with the root fingerprint. | Require HTTPS, fingerprint verification, and certificate-valid clients; never add an insecure TLS bypass. |
| 8 | Network isolation | medium | A CA reachable beyond the intended private network increases issuance attack surface. | Bind enrollment only to the selected private interface or private overlay; no public port and no Caddy admin API exposure. |
| 9 | Trust boundary | medium | Compromise of the online intermediate can issue trusted leaves. | Keep the offline root separate when the production PKI phase lands; scope this slice to organization HTTPS leaves and preserve dual approval. |
| 10 | Resource management | low | CA requests consume CPU/storage but are bounded for the expected small fleet. | Apply restart, log rotation, healthcheck, memory and CPU limits; rate-limit enrollment at DPF ingress. |
| 11 | Operational security | medium | Certificate lifecycle must be visible and renewable before expiry. | Emit issuance/renewal evidence, health status, expiry warnings, and recovery guidance; later mTLS work adds revocation operations. |
| 12 | Supply chain | medium | The project is active, but private-CA defects have high impact. Critical ACME/SCEP advisories affected `<=0.28.4` and SCEP `<0.30.0`; both are patched in 0.30.2. | Pin digest, monitor advisories, re-evaluate on every version bump, and do not enable SCEP. |

## Compliance and architecture fit

- **License:** Apache-2.0, compatible with DPF distribution.
- **Data residency:** fully self-hosted; certificate metadata and keys remain on
  the installation. No hosted Smallstep service is used.
- **Regulatory:** not an AI system and introduces no new personal-data flow.
  Key custody, audit, and retention remain normal security controls.
- **Fit:** extends the existing `docker-compose.tls.yml`, Edge PKI roadmap, and
  federation trust boundary. It does not replace `FederationLink`, dual
  approval, projection policy, or local backlog authority.

## Integration evidence

On 2026-07-20 the pinned multi-architecture image was pulled and started in an
isolated Docker container with a disposable volume and loopback-only random
host port. `step ca health` returned `ok`, a 64-character SHA-256 root
fingerprint was produced, and both the container and volume were removed. The
resolved image digest matched the approved digest above.

## Conditions

1. Pin the exact image digest and re-evaluate every version change.
2. Do not enable SCEP; enable ACME only if a later reviewed slice needs it.
3. Keep CA passwords in file-backed secrets and keys in the dedicated PKI
   volume; never log or serialize them to the backlog/federation plane.
4. Expose the CA only on an explicitly selected private address/network.
5. Federation pairing still requires candidate validation, matching-code dual
   approval, scoped projection review, and revocation; PKI is transport trust,
   not business authorization.
