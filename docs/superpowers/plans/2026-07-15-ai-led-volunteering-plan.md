## ⚠️ CRITICAL FINDING (2026-07-15, mid-build) — proactivity level ≠ autonomy
`DEFAULTS_BY_LEVEL` in `apps/web/lib/proactivity/proactivity-resolver.ts` maps even **assertive → `actionBoundary: "propose"`** — NO base proactivity level yields `preauthorized`. This is the platform's deliberate axis separation (memory: "proactivity = cadence NOT autonomy"; advise-mode strips write tools). So **auto-claim (acting autonomously) is NOT unlocked by a high proactivity LEVEL** — it requires a **pre-authorized POSTURE** (act-mode / `ResolvedDelegatedPosture`, `apps/web/lib/proactivity/delegated-posture.ts`), a separate governance axis the operator sets per coworker.

**CORRECTED (deeper dig): the autonomy authority is the work-management AUTONOMY ENVELOPE, not proactivity actionBoundary at all.** `preauthorized` is produced by NO code path in the repo (grep: only a defensive check + this module reference it) — so keying auto-claim on `actionBoundary` is dead/wrong. The real, governed autonomy axis is `apps/web/lib/work-management/autonomy-envelope.ts` → `resolveWorkCaseAutonomyEnvelope(input)` → `decisionMode: shadow-only | propose-for-approval | supervised-action | autonomous-action`, driven by the coworker's **trust level** and CAPPED by the item's **risk ceiling** + any **regulatory ceiling** (`AutonomyLevel` = shadow|propose|supervised|autopilot; autopilot→autonomous-action). Only `autonomous-action` permits an autonomous claim; funding a high-risk/regulated bet is correctly gated even for a high-trust coworker.

**Consequence for the build:** the pure core is now **corrected + tested** — `decideVolunteering(decisionMode: WorkCaseAutonomyDecisionMode) → auto_claim | ask_first | observe` (autonomous-action→auto_claim; propose-for-approval/supervised-action→ask_first; shadow-only→observe). `volunteerForFundedItem` must call `resolveWorkCaseAutonomyEnvelope` for (coworker trustLevel × item risk × ceilings) and feed its `decisionMode` into `decideVolunteering` — NOT the proactivity plan. ⚠ Remaining substrate to resolve before orchestration: where a coworker's `trustLevel` (AutonomyLevel) is stored/resolved, and how to classify a BacklogItem's `RiskClass` for the envelope input (reuse `fundingRiskTier` in demand-scoring-pack.ts? map to RiskClass). Proactivity still has a role — as the CADENCE/notification posture on the resulting run + the ask-first attention item — but NOT as the act/auto-claim gate.

This two-step discovery (proactivity level ≠ autonomy → the envelope IS the autonomy axis) is exactly why the orchestration is deferred to a focused session rather than rushed: an auto-claim keyed on the wrong primitive would have shipped either dead code or an over-autonomy governance defect. Built + committed this session: corrected pure `apps/web/lib/demand/volunteering.ts` + tests (3 pass). Orchestration (`volunteerForFundedItem` + funding-handler hook + attention item + bet-card render) is the focused-session remainder.

## 🚧 TRUE BLOCKER for the orchestration (needs a design decision, not a lookup)
The coworker "execution-claim trust" source-of-truth is **fragmented across two non-aligned enums**, and the envelope needs a concrete `trustLevel: AutonomyLevel`:
- `GovernanceProfile.autonomyLevel` — per-agent stored governance setting, values `supervised | constrained | autonomous` (seen in `aidoc-resolver.ts`, `agent-card-service.ts`, `orchestration/governance-profiles.ts`).
- Trust-graduation `AutonomyLevel` — `shadow | propose | supervised | autopilot` (`apps/web/lib/autonomy/trust-graduation.ts`, with `DEFAULT_RISK_CEILINGS`, `DEFAULT_THRESHOLDS`, `recommendTrustChange`) — the enum `resolveWorkCaseAutonomyEnvelope` actually consumes.

These **do not trivially map** (`constrained`/`autonomous` vs `propose`/`supervised`/`autopilot`). **Which is authoritative for a coworker's auto-claim authority, and the mapping to the envelope's `AutonomyLevel`, is an architecture decision** — it should go through `dpf-brainstorming` → `dpf-decision-via-kernel` (or an operator call), because getting it wrong ships a governance defect (a coworker auto-claiming when the operator only granted a supervised posture, or dead auto-claim). Do NOT guess it. Also needed: BacklogItem → `RiskClass` for the envelope (candidate: lift `fundingRiskTier` low/medium/high in demand-scoring-pack.ts to the `RiskClass` union). Until the source-of-truth is decided, the safe partial is the **ask_first-only** path (raise a needs-you gate on every funded bet), with auto_claim gated behind the resolved authority once decided.

## ✅ Source-of-truth RESOLVED + shadow-first increment shipped (2026-07-15, focused session)
The "which enum is authoritative" blocker is resolved, and a kernel decision set the shape.

**Source-of-truth found.** The coworker execution-trust dial is `TrustState.currentLevel` (schema `TrustState`, unique on `[agentId, activityType, riskClass]`, values = the trust-graduation `AutonomyLevel` shadow|propose|supervised|autopilot, with `regulatoryCeiling`). It is *operator-confirmed* via `recommendTrustChange` and is the enum `resolveWorkCaseAutonomyEnvelope` consumes — so the `GovernanceProfile.autonomyLevel` (supervised|constrained|autonomous) enum is NOT the envelope authority; `TrustState.currentLevel` is. **But** the schema draws a load-bearing line: *"these tables measure trust only; they do not authorize runtime autonomy changes,"* and `resolveWorkCaseAutonomyEnvelope` has **zero production callers** — auto-claim would be its first adopter.

**Kernel decision (`principle_decide`, in_platform_coworker, composite 9.10, margin 1.33, HIGH conf, no commandment conflict): `shadow_first`.** Beat `wire_now` (4.35 — crosses the "measure only" boundary as first-adopter; lost on Least-Privilege 0.35, HITL 0.36, Architecture-Over-Shortcuts, Never-auto-execute) and `capture_gap` (7.78). So: build the resolution + **shadow-record what auto-claim WOULD do**, keep the act ask-first, gate real auto-claim behind accumulated evidence + an explicit operator enable flag.
