1. Problem — the rule exists, but nothing scores real work against it

The kernel now says interface surface is failure surface: every new button or fillable field must earn its surface (justification + long-term reuse + clarification), and removing interfaces is favored (remove-avoidable-failure-opportunities, PR #1906). The scorer exists too — apps/web/lib/decision/ui-surface-features.ts (scoreUiSurfaceChange, PR #1910) turns a surface change into a pass / soft-block / no-op verdict.

But no code reads an actual Build Studio design and runs the scorer. Today a feature can add ten unjustified controls and the design gate says nothing. The rule and the scorer are inert because nothing supplies the scorer's inputs (controlsAdded/removed, justification, reuseBreadth, clarifiesOutcome) from a real design. Closing that — by system, not by a reviewer remembering — is the whole point of the principle.

2. Decision

Both forks were resolved by the live kernel (the principle_decide MCP tool on the reseeded, sign-corrected kernel — verified to match the pure engine):

  1. Source the rubric inputs from the design's formal SysML model, not a parallel markdown field. Kernel: sysml-sourced beat interim-markdown 11.23 vs 5.00 (high confidence), pulled by Single Source of Truth, Architecture Over Shortcuts, Research and Use Standards, Optimize for the Whole. A second markdown source would diverge from the SysML design representation and never feed the parity engine.
  2. Design this before building it. Kernel: spec-first beat just-build 10.59 vs 6.21 (high confidence) — the change touches the shared SysML vocabulary, so it is designed and reviewed before it becomes load-bearing across every design.

3. Position in the substrate — a slice of Phase 3, not a new island

The SysML Architecture Substrate spec already contemplates exactly this: §9 puts SysML into the work lifecycle, Phase 3 is "Build Studio planning hooks," and open question Q5 asks which gate owns mandatory SysML-note enforcement. This design is the first concrete instance of Phase 3 and a partial answer to Q5: the design-review gate owns interface-surface enforcement, sourced from the per-feature SysML architecture note.

It honors the substrate spec's discipline (§3 Non-Goals, §4, §13): no new EA tables, and no new element types in this slice — interface surface is modeled with the existing seeded sysml2 element types plus a property convention. A first-class ui-control element type is flagged as a future option "if proven insufficient" (§7 of the substrate spec already anticipates "future part/interface types if needed"), not introduced speculatively.

4. Notation — interface surface in design SysML (existing types + a convention)

A design author models the feature's interface surface inside its SysML architecture note using elements already seeded by seed-ea-sysml2.ts:

Rubric inputSysML representation (existing element types)
A control (button / fillable field / form / route)A part_usage carrying properties.uiControl ∈ {button, fillable_field, form, route} and properties.surfaceDelta ∈ {added, removed, changed}. No new element type.
controlsAdded / controlsRemovedCount of uiControl part usages by surfaceDelta.
justification (none/weak/researched)The requirement that satisfy-s the control. researched = the requirement carries a sourceKey/citation; weak = a bare requirement; none = no satisfy-ing requirement. "We might want it" never reaches researched.
reuseBreadthThe control's allocates fan-out — how many value streams / parts it is allocated to (and how many requirements it satisfies). Broad fan-out → high reuse.
clarifiesOutcomeA satisfy-ing requirement tagged properties.intent: clarification with a stated better-outcome.

This reuses the substrate's own grammar: requirement carries the rationale (exactly as seed-ea-sysml-data-authority.ts does today), and allocates is inherently one-to-many, so reuse breadth is structural, not asserted.

5. The SysML v2 model

The governance gate and an example feature's surface, in SysML v2 textual notation:

package InterfaceSurfaceGovernance {

  // ---- Governance obligations ----
  requirement def R1_EarnSurface {
    doc /* Every new interactive control must earn its surface: justified by
           research, reused across multiple internal outcomes, or it scores
           against remove-avoidable-failure-opportunities. */
  }
  requirement def R2_RemovalFavored {
    doc /* A net removal of interface surface scores favorably. */
  }
  requirement def R3_DesignSourced {
    doc /* Rubric inputs come from the design's SysML note, not a parallel
           markdown field (kernel-ratified: sysml-sourced). */
  }
  requirement def R4_SoftBlock {
    doc /* Unjustified net-new surface soft-blocks design advancement;
           overridable, with the override recorded as evidence. */
  }

  // ---- Interface surface: existing part usages + a ui-control property tag ----
  part def UiControl;   // realized by part_usage + properties.uiControl; NO new element type

  // Example design-time surface (status: planned) for a "register a truck" feature
  part addTruckButton : UiControl;  // properties { uiControl: button, surfaceDelta: added, intent: clarification }
  part truckVinField  : UiControl;  // properties { uiControl: fillable_field, surfaceDelta: added }

  // ---- Justification = a satisfy-ing requirement (researched carries a sourceKey) ----
  requirement def REQ_InlineTruckReg {
    doc /* Dispatchers register a truck inline; 4/5 pilot dispatchers abandoned
           the separate fleet page. provenance: architect; sourceKey: research/dispatch-pilot. */
  }
  satisfy REQ_InlineTruckReg by addTruckButton, truckVinField;

  // ---- Reuse breadth = allocates fan-out (3 value streams -> high reuseBreadth) ----
  allocate addTruckButton to fleet_dispatch_vs, parts_inventory_vs, warranty_vs;

  // ---- The gate behaviour + its verification ----
  action def ScoreInterfaceSurface;  // reviewDesignDoc extracts ui-controls and scores them
  verification def V_GateScores {
    doc /* reviewDesignDoc persists designReview.uiSurfaceAssessment and
           soft-blocks low-scoring net-new surface. */
  }
  verify R4_SoftBlock by V_GateScores;

  allocate ScoreInterfaceSurface to
    "apps/web/lib/mcp-tools.ts#reviewDesignDoc",
    "apps/web/lib/ea/ui-surface-extractor.ts",
    "apps/web/lib/decision/ui-surface-features.ts#scoreUiSurfaceChange";
}

6. Extractor — reuse the parity-engine pattern

A pure module apps/web/lib/ea/ui-surface-extractor.ts reuses the parse → buildDesired(descriptor) → diff contract from architecture-parity.ts / data-model-mirror*.ts:

  • parse the design's SysML note → the uiControl part usages, their satisfy-ing requirements, and their allocates edges.
  • buildDesired → a UiSurfaceChange (the deriver's input type): controlsAdded/removed from surfaceDelta counts; justification from the satisfy-ing requirement's provenance/sourceKey; reuseBreadth normalized from allocates fan-out; clarifiesOutcome from intent: clarification.
  • feed it to scoreUiSurfaceChange() (#1910), which already frames the decision as ship-as-designed vs retire/rework through principle_decide.

Pure and deterministic — no LLM in the gate inputs (consistent with size-design-doc.ts's stance), versioned and fixture-tested like the Prisma adapter.

7. Gate wiring

At the reviewDesignDoc handler (apps/web/lib/mcp-tools.ts), right after sizeDesignDoc:

  1. Extract the design's interface-surface change (§6) and call scoreUiSurfaceChange.
  2. soft-block-override on a soft-block verdict (the kernel's chosen enforcement strength): unjustified net-new surface holds advancement, surfaces the rubric tier + the contribution ledger, and an operator can override — the override recorded as evidence.
  3. Persist the verdict to designReview.uiSurfaceAssessment (parallel to sizeAssessment) and file an EaConformanceIssue when the design's SysML drifts from its realized controls (reusing existing finding substrate, not a new table).

8. Verification

  • Pure unit tests for the extractor (parse/diff, fixture SysML notes) and the existing deriver tests (#1910, 15/15).
  • A reviewDesignDoc snapshot/unit test asserting a low-scoring net-new surface soft-blocks and a justified/reusable one passes.
  • Runtime EA + Build Studio flow verification in the shared nonprod environment — deferred from the worktree per the substrate spec's stance (§10/§13), confirmed on the rebuilt portal.

9. Risks

  • Over-modeling (substrate §13): only controls whose surfaceDelta changes are modeled; a feature touching no interface surface produces no uiControl elements and the gate is a no-op.
  • Per-feature SysML dependency: this needs the design to carry a SysML architecture note. That is exactly substrate Phase 3 — this design gives Phase 3 its first concrete consumer rather than waiting for it. Until per-feature notes are routine, the gate no-ops when no SysML note is attached (fail-open, observable), so it never blocks a markdown-only design — it only bites once a design is modeled.
  • Soft-block false positives: heuristic justification reading can mis-grade; the override valve (recorded) is the mitigation, and the verdict is advisory-with-teeth, not a hard gate.
  • Notation drift toward a new element type: if the property convention proves insufficient for clean extraction, promote ui-control to a seeded element type via a follow-up — a notation-extension decision gated by verify-substrate-before-proposing-new, not a default.

11. Phasing & open questions

Phasing (each a small PR): (A) the pure extractor + fixtures; (B) the reviewDesignDoc wiring + uiSurfaceAssessment persistence + soft-block; (C) the notation-convention guidance in the dpf-sysml-architecture-substrate skill so design authors model interface surface consistently.

Open questions for operator review:

  1. Fail-open vs prompt when a design has no SysML note yet — no-op silently (proposed, during Phase-3 adoption) or surface "model your interface surface to be scored"?
  2. Should the gate run at design review only, or also re-check at plan/ship against the realized diff (catching surface added after design)?
  3. Promote ui-control to a first-class seeded element type now, or hold to the property convention until extraction proves it insufficient (proposed: hold)?
