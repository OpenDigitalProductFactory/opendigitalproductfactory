## Problem and decision boundary

The delivered BI-F646BC4E writer fence and PostgreSQL composition proof do not establish the remaining canonical served missing-fence refusal. Public MCP intentionally cannot supply trusted TaskRun/fence context. A normal executor signs its captured fence, while a supervised Workroom session lacks the independent writer grant. Waiting for an incidental legacy callback has no finite procedure.

The proposed scenario observes a **genuine independently produced writer payload** at its normal dispatch boundary. Before that original invocation publishes anything, the server makes one tightly bound legacy-form probe through the actual authenticated MCP route, omitting only the execution fence. After a verified refusal with zero canonical effects, the original invocation continues with its original captured fence and payload. It does not substitute an assessment, force approval, create a provider-free reviewer, split admission from execution, or retry a historical task.

This is an independently shippable verification capability under BI-26EB2F63, not an expansion of the delivered repair's implementation scope. BI-F646BC4E retains its served acceptance obligation until genuine evidence satisfies it. Capacity recovery BI-7CCCA696, canonical identity BI-CAP-437F7745 and role/room configuration BI-56E9CEC2 remain separate.

The item remains design work in triage. The current source reservation, sequence 24, is **HIGH / access-control**, with effective **Large** due to the actual transport-auth scope. Fifteen paths are reserved; three others overlap WC-6CCF8DAB / BI-BCBCA8D1 and remain unclaimed here. Implementation admission is input-required: research, design/spec/architecture, objective baseline, plan review and coverage remain pending. See the plan's exact claim/impact table. No approval, implementation, source test or deployed pass is inferred from reservation or this draft.

## Contracts

### C-SV-AUTH — authority and target containment

Only resolved development/test installations qualify. Unknown environment, production, paired-peer targets, missing current permission or an inactive/mismatched lease refuse. The existing shared-persona production override never authorizes this scenario.

Use the genuine requester's current OAuth connection and acting coworker. Reuse the existing verification environment, lifetime, owner, coworker-grant and exact-room/lease predicates from `govern/automation-fixture.ts:42–90`, while keeping resource-creation permissions and ordinary review authorization at their existing owners. Extract shared predicates; do not call `prepareFixture` to mint a user. The scenario creates no human/assistant identity, OAuth credential, consent, role or grant. Its internal probe session is narrowly derived from the actual captured reviewer authority.

This choice follows current source: `mcp/independent-review-request.ts:86–94` validates actual current non-credentials OAuth; `backlog/initiative-readiness/server-reviewer-dispatch.ts:332–356` requests independent review on the author's real connection; `reviewer-identity.ts:86–101` supports an independent coworker on a one-human installation. A second human or isolated fixture-user OAuth connection is unnecessary. A credentials-client token, browser session alone, cached authorization or a server-synthesized approval remains insufficient. Actual reviewer/provider readiness is still UNVERIFIED.

Use one fresh, explicitly disposable **feature/Large** fixture subject with two sequential ordinary cases: design-spec gate receipt, then spec-approval/baseline after re-reading the normal issuer. The fixed specimen must truthfully describe its Large feature scenario and be classified/admitted normally; no override manufactures an owed gate. Medium is the wrong fixture shape because `shape-requirements.ts:154–169` uses its body baseline lane; Large retains ordinary design/spec gates (`:191`). The fixture shape does not authorize BI-26EB2F63 implementation: that work's actual transport/auth paths must receive fresh sensitivity and native shape assessment. Source delivery includes one self-contained fixture design at the fixed **flat** path `docs/superpowers/specs/review-writer-fence-verification-fixture.md`. This future file requires its own implementation-phase claim and genuine DCO publication; it is not created or claimed by this two-document draft. Its text is review material, never a canned assessment. Real reviewers may refuse it.

Preparation is finite but includes ordinary source work. Initial prepare creates only the owned subject/run and returns an authenticated setup handle. The executing assistant then creates and publishes a genuinely distinct governed fixture worktree/branch at the actual signed source commit containing the fixed file, and claims/adopts that source for the new subject through existing tools. One subject may use its own branch for both gates. Never reuse or rebind BI-26EB2F63's branch: `work-capsule-store.ts:200–267` and branch identity key adoption by repository plus branch and reject a different bound item. The server performs no Git mutation, invents no refs, and accepts no caller-selected child or artifact path.

Final prepare derives the actual child room/source tuple from the initial owned subject and current canonical records. It verifies one exact room, real branch/base/head, repository/provider file identity, DCO and accountable author through the existing resolver. `canonical-artifact-discovery.ts:297–375` accepts the one explicit live-body spec path at the recorded head even if unchanged on the fixture branch. `repository-artifact.ts:341–507` checks exact subject/room/head and genuine DCO/owner provenance. A shared commit is acceptable only on the genuinely distinct published branch and independently valid owned claim; copying source strings is not adoption. Current OAuth Workroom creation records the agent principal as createdBy and the human as requestedBy (`work-capsules/handler-actor.ts:17–25`, `oauth-workroom-ownership.ts:7–12`). Repository authorship uses that actual createdBy principal, not an assumed requester or copied parent author. The unique real DCO email must pass current alias checks against it; unknown/conflicting identity refuses and is reported truthfully. No identity repair, alternate credential or fabricated author is part of this scenario. The baseline writer also requires a flat path (`baseline-repository.ts:299`).

Use unchanged canonical discovery, pre-baseline recovery issuance and the repository review reader. Do not add managed-document issuer/reader support: current managed resolution does not supply the pre-baseline packet or normal design reader, and extending those only for this test is unnecessary. An existing baseline, review receipt or approval is never seeded. Every prerequisite and returned gate request remains subject to normal readiness and authority; if the requested gate is not owed, the scenario cannot manufacture it.

Repository spec approval may create a content-addressed archive before its fence check. Measure and disclose that archive effect separately. AC-SV-3 requires zero **new receipt, baseline and pin** effects; it does not require zero total database writes, and actual audit records must exist. No missing-fence refusal after a prior winner qualifies as the new-effect negative case.

### C-SV-BOUND — completed preparation provenance and atomic admission

Expose only one closed fixed-scenario lifecycle through the existing verification pack: prepare, start, observe and retire an issued run. This is a new narrowly scoped served registration requiring implementation claims and normal capability/audit metadata, not an already available tool or a generic scenario catalog. It reuses the normal task service and reviewer loop. Preparation creates only the fixed disposable subject/run under current genuine authority, then finalizes after genuine source publication and adoption. The initial prepare audit proves setup ownership but cannot admit a review; only the completed final prepare result can. Start uses the subject's actual issued review packets and normal `authorizeCoworkerRequest`/external adapter; it cannot submit a caller-authored packet or bypass a review gate.

Use **completed canonical preparation ToolExecution provenance** as the initial root. `mcp-governed-execute.ts:736–782` persists/finalizes the handler's audit and returns its handle after the handler finishes. Therefore preparation and start are distinct governed calls; preparation never dispatches a review before its audit exists. The returned handle is a locator only. Start reads the actual row and requires the exact fixed prepare operation, successful final result, `external-jsonrpc` execution source, real actor/agent/token binding and exact server-generated run/resource manifest. It revalidates current OAuth, permissions, room, lease, source and immutable expiry independently. An absent, metrics-only, reserved, failed, mismatched or partially finalized audit cannot authorize a start. Register this fixed lifecycle tool explicitly with `sideEffect: true`: preparing/finalizing creates or changes its journal/subject. Existing `tool-audit-helpers.ts:4–13` then selects ledger audit and `governed-tool-audit.ts:69–71,105` retains the full redacted result, as the current UX verification tool already does. A registered-metadata/governed-wrapper regression must prove ledger class, exact completed manifest result, real actor and token attribution; retainAuditParameters alone is insufficient. Record the actual server-provided authorityDecisionId in the protected journal, never a caller value. No global audit-policy change or conflicting workroom dependency is needed.

The root manifest binds the existing RuntimeVerification internal/public IDs, fixed scenario/schema version, real requester/coworker, parent room/lease, original absolute expiry, the exact fresh subject, child room, published source tuple/provider blob and content digest. Generic RuntimeVerification result, command, caller-supplied tool-execution references and prompt markers are never authority: every field used for admission must match the canonical prepare result, the protected server-owned preparation journal and current records. Copying a report to a new verification ID or changing a child target fails. The initial root needs neither a synthetic TaskRun nor a new signing key/HMAC capability.

On ordinary task admission, use the current server-only `admissionGuard` and `afterTaskCreated` in `tak/autonomous-work-run.ts:149–177` to insert an immutable TaskArtifact manifest atomically with the real TaskRun. Compose the closed scenario hook where `mcp-task-submit.ts` currently threads reassessment hooks; do not borrow reassessment authorization or create another task creator. Use a deterministic unique artifact identity keyed by prepared run and fixed case. The actual TaskRun/request digest, selected reviewer, original source, subject/artifact, writer/gate and expiry are immutable values. Concurrent starts or changed request/task IDs cannot create a second execution for one case; a uniqueness conflict rolls back the new task. TaskRun metadata is only a locator.

Production source search found TaskArtifact creation sites and no update/delete/upsert sites in the inspected app/package code; `build-delivery.prisma:1275–1288` supplies unique `artifactId` and the internal TaskRun relation. That supports append-only records, but does not replace retention and adversarial tests. Current JSON metadata is not inherently immutable. Preserve subject-creation locks, quarantine and all current authority revalidation. No scenario flag enters the immutable owed-review packet.

Make initial preparation crash-safe with one typed journal in the existing RuntimeVerification model. Use existing kind `manual-review` with a closed server-owned scenario result key and verification-ID prefix; add no kind or schema value. Following `validateVerificationInput`'s existing reserved Small-acceptance-key guard, the generic runtime-verification recorder rejects either this result key or ID namespace regardless of caller kind. Only the fixed scenario owner may create or monotonically update its journal. In one transaction, create the journal and the single fresh subject through `ingestBacklogItem`'s existing injected store (`backlog-ingest.ts:165–200,371–375`), retaining actual actor/room/lease/expiry and exact created IDs before commit. Reuse its intake validation and move current knowledge indexing/advisory work after commit as a narrow shared refactor, rather than duplicating ingestion or holding network work under a transaction. Either creation rolls back completely or an exact server-owned cleanup journal survives a crash. A journal has cleanup authority over only its actual resources; it cannot admit a review without the separate completed final preparation audit. Current generic runtime recording is create-only, and existing automation retirement updates only ux runs; protect and regression-test all entry/update paths. No new model, HMAC, synthetic task or audit-reservation port is required.

### C-SV-CONSUME — one-shot state and races

The scenario's evidence progression is separate from TaskRun status:

`prepared -> admitted -> writer-payload-ready -> probe-consumed -> negative-verified -> original-effect-observed -> replay-observed -> settled -> retired`.

Refused, failed, canceled, expired, timeout and UNKNOWN observations are retained; none transitions to passed merely through cleanup.

At the writer boundary, validate the exact current association and original captured generation. Check that no qualifying winner exists, then claim one probe atomically with the existing task/CAS transaction pattern. Key the unique probe claim by the admitted run and fixed case; keep its already-bound task, canonical payload digest, original fence digest and deadline as values, never as key material that a changed task or payload could use to obtain another claim. Release all transaction locks before any HTTP dispatch. Concurrent callbacks cannot consume twice. A duplicate original callback reaches neither repository writer while the probe is pending or UNKNOWN. Only the unique claim owner may continue after the qualifying negative observation is durably verified; every other observer reads retained state and performs no dispatch. Outbound consumption does not deduplicate received HTTP requests. At the authenticated pack dispatch boundary, after current governed authorization/audit reservation but before either canonical writer, atomically insert a deterministic append-only receive artifact under that same outbound claim. Only its first owner may invoke the writer. The receive key is fixed by the claim, never by transport request ID or token. An identical token/payload replay returns the retained exact probe result or pending/UNKNOWN without dispatch; each actual request keeps its normal authorization and audit. Received means spent even if the process crashes before the writer. A crash or missing result never transfers ownership, creates a new receive key or authorizes another send.

Use protected monotonic persistence outside replaceable progress text. Current terminal progress reconstruction retains only selected fields, so a new progress key alone is insufficient. Prefer append-only TaskArtifact claim/result records with deterministic identities: `artifactId` already has a unique constraint in `packages/db/prisma/schema/build-delivery.prisma`. TaskRun metadata remains a locator, not another consumption authority. The initial unique insert supplies the one-shot claim; subsequent exact result inserts retain evidence under that claim. Q-SV-3 must prove all mutation, retention and reconciliation paths preserve this authority before implementation. A signed RuntimeVerification result is insufficient: replaying an earlier armed JSON value must never reset consumption.

Claimed means spent even if the process crashes before dispatch. An absent response is not evidence the request never executed. Restart/reconciliation may observe receipts and audit for that original claim; it cannot reissue it or invent a new generation. Cancellation, expiry, quiescence, changed actor/source, predecessor quarantine or an execution hold wins over further probes.

### C-SV-TRANSPORT — real route and genuine payload

The common hook is inside the existing initiative-readiness handler, after its normal authorization/binding/payload checks and immediately before `recordInitiativeGateReceipt` or `recordInitiativeSpecApproval`. It runs outside the repository's TaskRun/subject locks.

Only a genuine pending writer invocation with the original valid captured fence can enter the hook. The server derives a short-lived legacy-form session from that invocation's actor, task, thread, route, current capability and exact narrowed scopes, omitting the fence. It keeps the JWT internal and calls the canonical same-installation `/api/mcp/v1` route with the actual writer payload. The URL comes from existing trusted portal configuration, never caller input; origin/TLS rules are unchanged.

The nested probe passes normal transport authentication, current user/coworker permission intersection, policy, approval and writer validation. It obtains its own real authorization decision. No fabricated decision row, stronger scope, permit reuse, forced approval or bypass header is allowed. Missing original fence plus the spent claim prevents recursive probing.

The qualifying negative result is the writer's exact held/uncertain/unversioned/displaced new-effect refusal, accompanied by persisted matching task/authority audit and zero new receipt, baseline and pin effects for the scoped subject. A generic permission denial, malformed artifact, source-access failure, approval request, existing winner or failed route does not qualify.

After that verified negative, the original invocation proceeds once with its original captured fence and unchanged genuine payload. Its ordinary repository transaction rechecks authority, generation and artifact. A concurrent cancellation or generation change may correctly refuse it; do not recapture a newer fence. The probe does not alter provider routing, model, budget, loop history or writer-correction budget.

AC-SV-4's replay runs inside the same original authenticated handler, immediately after the canonical repository method reports a genuine new effect and before the handler returns to normal task settlement (`initiative-readiness-pack.ts:469–532`). The unique claim owner rechecks current task/generation/expiry, then calls the same unchanged repository method once with identical normalized arguments and original captured authority. Require `deduplicated: true`, the same receipt/baseline identity and no additional pin. This is a canonical repository replay within the real served invocation, not a second HTTP request, reviewer assessment or ToolExecution; record that provenance exactly. Do not replay an initially deduplicated, failed, expired or UNKNOWN result. If cancellation or uncertainty intervenes, retain the actual first effect and nonpassed replay status; no retry or fence recapture. Both repository methods already expose their deduplicated result, and normal handler return precedes task-owner settlement.

### C-SV-OUTCOME — audit and uncertainty

Keep every actual ToolExecution, authorization decision and server result. The control probe must be explicitly distinguishable from the reviewer's real final writer attempt in native folding and terminal classification. Only authenticated server control provenance, checked against the consumed claim, may supply that distinction. Bind it to the exact run/case/claim, original task, writer name and canonical payload digest, and revalidate before route dispatch. A token for one probe cannot be reused for another tool or changed arguments within the reviewer's broader grant set. Strip caller purpose markers and restore the audit marker only from verified server context. Missing/invalid purpose validation refuses control use; it never silently downgrades to an ordinary or hidden attempt. Caller parameters, arbitrary `_meta`, a request ID or a public purpose flag cannot hide a refusal.

The current audit writer strips untrusted `_taskExecutionFence` and restores trusted context. Preserve that behavior. Add one closed signed internal-session purpose record containing schema/scenario version, prepared run ID, case key, admission-artifact ID, spent probe-claim artifact ID, original task ID, exact writer tool, canonical payload digest, captured-fence digest and absolute expiry. The server signer alone derives it from the unique owned claim; omit the actual taskExecutionFence from this legacy-form session. Token actor, user, task and existing authority scopes stay bound to the original execution. Transport and the writer boundary must resolve both immutable artifacts, compare every field and current expiry, and require the probe claim to be spent by this exact owner before dispatch. Only that verified context supplies the audit marker. It grants no additional tool or target authority; malformed, copied, stale, cross-task or changed-payload purpose refuses. The normal original invocation has no control purpose and retains its ordinary audit/count. No caller field or fallback can relabel an ordinary writer execution.

The nested request has one finite deadline capped by the fixture expiry, lease, original task deadline and an implementation-reviewed per-call bound. No unbounded polling, provider call or new queue is introduced. On timeout, lost acknowledgement or ambiguous result, record UNKNOWN/timeout and stop the positive continuation. Never blindly treat network abort as server cancellation. The normal task owner must retain or settle through its existing fenced lifecycle without resetting uncertainty. Transport-to-owner propagation must prevent automatic model correction or probe replay; prove both native CLI and ordinary agentic-loop paths before acceptance (Q-SV-4).

Unexpected probe publication is a **failed safeguard verification**. Preserve the actual effect and audit, do not delete them to restore a clean-looking fixture, and do not count winner readback as the planned positive new-effect case. A genuine reviewer FAIL is an assessment result, not a fabricated PASS. Baseline-positive coverage stays unrun if the independent reviewer never proposes approval.

Ordinary RuntimeVerification evidence remains a report. The reserved scenario journal has only the exact cleanup/lifetime role described above; admission additionally requires final canonical preparation audit, and one-shot consumption belongs only to TaskArtifact. Persist runtime image/commit and containing release, source identity, scenario version/run, request/task/artifact digests, reviewer/author/authority references, consumed claim, negative and original tool execution IDs, exact receipt/baseline/pin deltas, timestamps, observed failure class and cleanup state. No raw signed token, authorization code, cookie, secret, refresh token or PKCE verifier enters evidence.

### C-SV-CLEANUP — exact-resource retirement

Each child remains a normal TaskRun owned by the genuine requester and independently executed by its selected reviewer. The normal executor/settlement path owns completion; the probe never independently declares the original complete. Load only child task, subject, artifact and room IDs from the authenticated preparation/admission manifests. Supported cancellation or room closure may affect only those resources and must be observed settled. Do not scan the real user's full task/room inventory or reuse `retireFixtureRun`'s fixture-user credential and identity mutations.

AC-SV-5's credential retirement is conditional: **no fixture credentials are created in this design, so credential retirement is NOT_APPLICABLE**. The operator's connection, consent, tokens, refresh tokens, groups and identity remain untouched. Retire the scenario's own admission/probe authority after all manifest-owned work settles; retain artifacts, receipt/baseline/pin and audit history. Disposable resources are closed/archived through ordinary authorized operations, never deleted to hide a result.

The original absolute expiry denies new start/probe activity independently of cleanup. Extend the existing bounded verification cleanup mechanism with exact manifest ownership, a bounded batch/cursor and the same original deadline; no user-wide scan, new queue or lifetime renewal. An UNKNOWN child can keep cleanup pending: expose its exact owner and supported reconciliation action, without clearing UNKNOWN, force-closing it, or inferring task settlement from HTTP abort. Cleanup and verification verdict remain separate.

## Scale, refactoring and compatibility

Ceiling: one run per existing owned verification lease, one fresh subject with at most two fixed review cases, one probe per case, one original invocation and one qualified winner replay per case. Ordinary review/provider budgets and the fixture's existing absolute lifetime remain unchanged. Exact-ID reads and indexed expiry paging avoid whole-inventory scans. Any general scenario catalog, higher fan-out or cross-installation behavior is outside BI-26EB2F63 and requires reviewed scope under EP-ABB3AC9D.

Allocate approximately 20% of effort to consolidating current fixture lifetime/ownership predicates, atomic task association and CAS/result preservation. Extract only repeated mechanisms; keep review authorization and writer semantics at their existing owners. No new task executor, queue, identity kind, permission grant or evidence ledger.

Ordinary non-fixture requests and both canonical writers retain their behavior. A malformed/absent fixture association cannot enable control behavior. Public and internal token verifiers remain backward compatible: ordinary legacy tokens still lack a fence and are governed normally. Existing fixture retirement and no-fixture browser sign-in retain their contracts.
