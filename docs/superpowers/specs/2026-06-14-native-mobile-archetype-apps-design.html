This design answers a single question: what do native iOS/Android apps for DPF look like — serving both the platform itself and the real-world use cases of each archetype (a salon's customers booking visits; an HVAC company's field techs running jobs) — and how do we build, route, test, and ship them given that DPF installs one-org-per-install on the customer's own hardware.

1 · Executive summary — the reframe

"We never moved past basic backend" undersells what's on disk. There is a substantially-built Expo / React Native app at apps/mobile/ (Expo SDK 55, RN 0.83, React 19.2, Expo Router, Zustand, NativeWind), a complete REST surface at apps/web/app/api/v1/*, shared @dpf/api-client / @dpf/types / @dpf/validators packages, JWT + refresh-token auth, Notification / PushDeviceRegistration models, an offline cache, a dynamic form/view renderer (camera, signature, location, charts), and Maestro E2E flows. It is typechecked and unit-tested in CI.

But what's built is one product for one persona. The existing app targets the platform operator/builder — epics, backlog, portfolio, approvals — and the May 2026 audit deliberately narrowed its first release further to Paused-Work HITL approvals. That is a real and useful product. It is not what this goal asks for.

You are asking for a second product line: archetype end-user apps — the org's customers and its field employees — and you've already named the key insight: "all can use the same app, predicated on their persona and use case." That is exactly right, and the substrate to do it (archetypes, roles, work items, customer estate, dynamic rendering) is already in the schema.

The three real gaps — none of them "the basics":
  1. Connectivity / discovery. One app-store binary must reach N self-hosted single-org installs. Today the server URL is hard-coded at build time (EXPO_PUBLIC_API_URL), so the app reaches exactly one install. This is the routing problem you flagged.
  2. Persona-driven runtime UX. The app's tabs are static and operator-only. We need a manifest the install returns at login that drives which mode (customer / field / operator) and which screens the user sees — so one binary serves every archetype and persona.
  3. Native build & release. iOS binaries cannot be built in our Linux Build Studio (or any Linux box) — they need macOS + Xcode. We stand up EAS (Expo's cloud) to compile and ship, and you complete the store/account steps no agent can.

Bottom line: we are one product (operator companion) in; we add two persona modes (customer, field) on the same shell, solve discovery once, and stand up the cloud build pipeline. The heavy lifting is integration and one keystone abstraction — not greenfield.

3 · Keystone architecture — the install drives the app

The whole design hinges on one move: the app is a generic renderer; the install drives both its design and its functionality. After the user connects to their org's install and signs in, the app fetches one install manifest carrying three layers — (1) design tokens (the install's branding/theme as data), (2) capability gating (which functionality this org + archetype + persona may use), and (3) server-driven screens (the forms, views, tabs, and navigation, as data). The app re-themes and re-functions from that manifest plus a fixed catalog of native components. No per-company or per-archetype code ships in the binary — uniqueness is data the platform emits, exactly the way an archetype already bootstraps a portal.

The install manifest (new contract — three layers)

// GET /api/v1/app/config — returned after connect + login; drives the whole app
{
  "schemaVersion": "1",
  "org":     { "name": "Acme HVAC", "archetype": "trades-maintenance/hvac-contractor" },
  "persona": { "kind": "employee", "mode": "field" },

  // (1) DESIGN — W3C DTCG design tokens, sourced from the install's BrandingConfig.tokens
  "designTokens": { "color": { "accent": { "$type": "color", "$value": "#1e6f50" } },
                    "font":  { "body":   { "$type": "fontFamily", "$value": "Inter" } } },

  // (2) CAPABILITIES — derived from the archetype activationProfile + org activation
  "capabilities": ["work-items", "scheduling", "offline-sync", "photo-capture", "signature"],
  "vocabulary":   { "customer": "customer" },   // archetype overrides (e.g. "patient", "member")

  // (3) SCREENS — server-driven nav + screens, rendered by the fixed native catalog
  "navigation": { "tabs": ["jobs", "schedule", "customers", "more"], "defaultTab": "jobs" },
  "screens":    [ { "screenId": "jobs", "type": "view", "schema": { /* DynamicViewSchema */ } } ]
}

Each layer composes substrate that already exists, rather than inventing it:

  • Design tokens → BrandingConfig.tokens (per-org JSON, light/dark) + the portal's --dpf-* variables in globals.css + the runtime injector buildBrandingStyleTag in apps/web/lib/release/branding.ts. The web portal already re-themes from these; mobile's theme.ts is hard-coded today and consumes them at startup instead.
  • Capabilities → StorefrontArchetype.activationProfile (modules + axes) + OrganizationCapabilityActivation (the org's on/off choices) + the nav capabilityKey / orgCapabilityKey gates in portal-navigation-model.ts.
  • Screens → DynamicFormSchema / DynamicViewSchema + fieldRegistry / widgetRegistry + FormRenderer / ViewRenderer in apps/mobile/dynamic/ (a working SDUI seed), plus the portal's ScreenManifest pattern as precedent for declarative screen contracts.

Identity is already converged for this. AGENTS §11 (principal convergence) resolves User, CustomerContact, Agent, and MobileDevice onto one Principal; the alias kind tells the platform which surface authenticated — so customer, employee, and operator are one identity model, three views, all selected by the manifest.

Standard, or do we invent?

Researched against the field (citations in §10). The verdict: this is a partially-standardized pattern — adopt the primitives, build only the glue. It is not genuinely novel; nobody ships exactly "generic RN app + token theming + native SDUI + capability flags + self-hosted multi-archetype" off the shelf, so the integration is ours — but every layer underneath is established.

Apple's declarative-only line (App Store 2.5.2)

Apple guideline 2.5.2 forbids apps that "download, install, or execute code which introduces or changes features." A JSON manifest of tokens + layouts rendered by pre-shipped native components is data, not code — and is permitted. Shipping server-delivered JS/native code that changes functionality is not. Guideline 2.3.1 also bars using config to change the app's core purpose post-review (per-archetype variation is fine; turning a wellness app into a casino is not). The contract stays strictly declarative — a fixed component vocabulary + tokens + capability flags + data — and we never ship executable code over the wire. (Android/Play has no equivalent restriction.)

4 · Repo & CI strategy — keep the monorepo, decouple the lane

Recommendation: keep mobile in the monorepo; do not split it out now. Mobile already consumes @dpf/api-client, @dpf/types, and @dpf/validators as workspace:*. A separate repo forces publishing and version-pinning those packages, which introduces contract drift between the API and its client and slows iteration — the opposite of the goal. The shared, always-in-sync API contract is the single biggest asset of co-location.

The "PRs take forever" pain is not caused by mobile being present. It's the apps/web four-shard vitest matrix plus the Next.js production build (15–20 min). Mobile changes neither need nor should wait on those. The fix is lane decoupling, not repo splitting:

  • Path-filtered mobile CI lane. A workflow that triggers only on apps/mobile/** + the three shared packages, running mobile typecheck + jest only. Web shards skip when a PR touches only mobile, and vice-versa.
  • Native builds off the PR gate entirely. EAS cloud builds run on merge-to-main / tag / manual dispatch — never blocking a PR. (iOS builds take many minutes on cloud macOS; they have no business in the inner loop.)

When to revisit a split: only if a dedicated mobile team with an independent release train emerges. Even then, prefer a published-contract package over a fork, so the API and client stay versioned together.

5 · Build & simulation — dev tools, cross-compile, and the iOS constraint

Hard constraint: iOS binaries can only be built on macOS + Xcode. No Linux cross-compiler exists. Our Build Studio sandbox is node:24-alpine (Linux), so it can never build iOS — and it doesn't build Android today either (no Android SDK / Gradle / Java).

The answer is to split "write & test code" from "compile native binary."

  • Code generation + unit tests (jest, typecheck): Build Studio, Claude, or Codex — all Linux, all fine. Build Studio stays viable for authoring and testing RN code; it simply does not compile the binary.
  • Native compilation (.ipa / .aab): EAS Build (Expo's cloud) runs macOS builders for iOS and Linux builders for Android. You do not need to own a Mac fleet for CI. A local Mac + Xcode is optional, only for deep local iOS debugging.
  • Store submission: EAS Submit → TestFlight and Play.

6 · Org-install connectivity — the hard problem, solved in phases

DPF is single-org-per-install on the customer's hardware, each with its own PUBLIC_URL and no central tenancy. A single app-store binary therefore can't "just know" where to connect. This is a solved pattern in self-hosted software — Mastodon, Nextcloud, Home Assistant, WordPress, and GitLab all ship one app and ask the user to point it at their instance, validated by a discovery endpoint. We adopt the same model.

Your worry — "how do we test with lots of manual setup if real phones are used" — is handled by a layered approach where physical devices cover only what simulators provably can't.

Kill the manual-setup tax with a seeded demo org. 10 · Research & benchmarking

  • Self-hosted multi-instance clients — one app-store binary + user-entered instance URL + discovery endpoint. Home Assistant is the closest product analog (point at your instance; its config + theme drive the UI — though via WebView); Nextcloud auto-syncs the server's theme to its apps and sells pre-configured "branded clients" as a premium; Mastodon exposes per-instance config via /api/v1/instance. Adopted: instance-URL entry + .well-known descriptor + manifest. Rejected as default: per-org white-label builds — offered only later as a premium.
  • Server-driven UI (SDUI) — Airbnb's Ghost Platform (reference design, not OSS), DivKit (VK, Apache-2.0, iOS/Android/web — no first-party RN renderer), and Adaptive Cards (declarative JSON UI with a real React-Native renderer, but card-scoped). Adopted: a declarative component-registry approach over our existing dynamic renderer. Rejected: downloading executable UI code (Apple 2.5.2) and over-scoped SDUI frameworks (Spotify deprecated its HubFramework).
  • Design tokens as data — the W3C DTCG Design Tokens Format Module reached its first stable version (2025.10). Adopted as the manifest's design layer; maps onto our existing BrandingConfig.tokens (Style Dictionary for build-time fan-out if needed).
  • Field-service apps (ServiceTitan, Jobber, Housecall Pro, FieldEdge): convergent field-tech feature set — job list, schedule, "on my way", check-in/out, line items, photos, signature, offline. Validates our WorkItem/WorkSchedule + dynamic camera/signature surface; offline-first is table stakes.
  • Customer booking apps (Mindbody, Fresha, Square Appointments, Calendly): book, reminders, rebook, pay, membership. Validates StorefrontItem booking schema + Invoice/Payment reuse.
  • Mobile toolchain: Expo + EAS is the current industry-standard managed RN pipeline (cloud iOS builds without a Mac fleet). Already chosen in apps/mobile — keep.
  • Anti-pattern rejected: "the whole portal on a phone" (the May 2026 audit's own warning). We render persona-scoped surfaces, never a shrunk desktop.

16 · SysML v2 architecture substrate

Per the EA convention, a design spec carries a SysML v2 viewpoint over the platform substrate — a notation for requirements, interfaces, allocations, and verification, not a separate model. The install manifest is the load-bearing new interface contract; below it is in SysML v2, traced to the existing substrate that realizes it.

package NativeMobileArchetypeApps {

  // ---- Systems ----
  part def MobileApp;               // one generic Expo/RN binary, published by Arcamanus LLC
  part def DpfInstall;              // a self-hosted single-org install
  part def NativeComponentCatalog;  // fixed, app-shipped renderer catalog (fields + widgets)

  // ---- Interfaces (the new contracts) ----
  interface def InstanceDescriptor {     // GET /.well-known/dpf-instance.json
    attribute instanceId : String;
    attribute orgName    : String;
    attribute archetype  : String;
    attribute authModes  : String[1..*];
  }
  interface def InstallManifest {        // GET /api/v1/app/config
    attribute schemaVersion : String;
    attribute designTokens  : DtcgTokenSet;        // (1) design  — W3C DTCG
    attribute capabilities  : Capability[0..*];    // (2) gating  — archetype-derived
    attribute vocabulary    : VocabularyOverride[0..*];
    attribute navigation    : NavigationSpec;      // (3) screens — declarative SDUI
    attribute screens       : ScreenSpec[0..*];
  }

  // ---- Ports + topology ----
  port def DescriptorPort { out descriptor : InstanceDescriptor; }
  port def ManifestPort   { out manifest   : InstallManifest; }

  part install : DpfInstall { port descriptorOut : DescriptorPort; port manifestOut : ManifestPort; }
  part app : MobileApp {
    part catalog : NativeComponentCatalog;
    port descriptorIn : ~DescriptorPort;
    port manifestIn   : ~ManifestPort;
  }
  connection connect : app.descriptorIn to install.descriptorOut;   // simple connect step
  connection absorb  : app.manifestIn   to install.manifestOut;     // absorb design + functionality

  // ---- Requirements ----
  requirement def R1_InstallDrivenDesign          { doc /* the install's design system drives the app's design */ }
  requirement def R2_ArchetypeDrivenFunctionality { doc /* installed archetypes drive exposed functionality */ }
  requirement def R3_SingleGenericBinary          { doc /* one binary; no per-company/per-archetype code shipped */ }
  requirement def R4_DeclarativeOnly              { doc /* manifest is declarative data only — Apple 2.5.2 */ }
  requirement def R5_InstanceDiscovery            { doc /* a simple connect step locates + validates the install */ }
  requirement def R6_OfflineCapable               { doc /* field use-cases work offline; writes queue + reconcile */ }

  // ---- Allocations: obligation -> existing substrate ----
  allocate R1_InstallDrivenDesign          to BrandingConfig_tokens, globals_css_dpf_vars, branding_buildBrandingStyleTag;
  allocate R2_ArchetypeDrivenFunctionality to StorefrontArchetype_activationProfile, OrganizationCapabilityActivation, portal_nav_capabilityKey;
  allocate R3_SingleGenericBinary          to MobileApp, NativeComponentCatalog, InstallManifest;
  allocate R4_DeclarativeOnly              to InstallManifest;          // schema carries data, never code
  allocate R5_InstanceDiscovery            to serverConfig_ts, InstanceDescriptor;
  allocate R6_OfflineCapable               to offlineQueue_ts, expo_sqlite_cache, DynamicFormSchema_offlineCapable;

  // ---- Verification ----
  verification def V_Connectivity { doc /* serverConfig 15/15 + full mobile suite 164/164 (shipped) */ }
  verification def V_Manifest     { doc /* drive connect -> manifest -> themed shell on the live install (P2) */ }
  verification def V_Declarative  { doc /* review: no remote-code path; EAS builds a fixed JS bundle */ }

  verify R5_InstanceDiscovery by V_Connectivity;
  verify R1_InstallDrivenDesign by V_Manifest;
  verify R4_DeclarativeOnly by V_Declarative;
}

Allocation targets map to real substrate: BrandingConfig.tokens + globals.css + branding.ts (R1); StorefrontArchetype.activationProfile + OrganizationCapabilityActivation + nav gates (R2); apps/mobile + the dynamic renderer + the manifest schema (R3/R4); serverConfig.ts + .well-known/dpf-instance (R5); offlineQueue.ts + expo-sqlite + offlineCapable (R6).

SysML architecture note

  • Scope: new mobile-client subsystem + the install-manifest interface; no change to portal data authority.
  • Requirements/constraints: R1–R6 (install-driven design, archetype-driven functionality, single generic binary, declarative-only, instance discovery, offline).
  • Interfaces/ports: NEW GET /api/v1/app/config (InstallManifest) + GET /.well-known/dpf-instance.json (InstanceDescriptor); existing /api/v1/* + JWT unchanged.
  • Allocations: as traced above — all to existing substrate except the two new endpoints + the mobile token/SDUI consumers.
  • Verification: V_Connectivity (shipped: 15/15 + 164/164), V_Manifest (drive on live install at P2), V_Declarative (review + EAS fixed-bundle).
  • Data authority: source of truth unchanged — the manifest is a derived projection of BrandingConfig + activationProfile + DynamicForm/View; no new authority, no new tables.
  • EA catch-up: add the mobile client + manifest interface to the platform-decomposition + authority views (none today).
  • Open architecture risks: SDUI screen-schema versioning/back-compat; JSON-parse latency on low-end Android; offline conflict resolution.
