This design answers a single question: what do native iOS/Android apps for DPF look like — serving both the platform itself and the real-world use cases of each archetype (a salon's customers booking visits; an HVAC company's field techs running jobs) — and how do we build, route, test, and ship them given that DPF installs one-org-per-install on the customer's own hardware.

1 · Executive summary — the reframe

"We never moved past basic backend" undersells what's on disk. There is a substantially-built Expo / React Native app at apps/mobile/ (Expo SDK 55, RN 0.83, React 19.2, Expo Router, Zustand, NativeWind), a complete REST surface at apps/web/app/api/v1/*, shared @dpf/api-client / @dpf/types / @dpf/validators packages, JWT + refresh-token auth, Notification / PushDeviceRegistration models, an offline cache, a dynamic form/view renderer (camera, signature, location, charts), and Maestro E2E flows. It is typechecked and unit-tested in CI.

But what's built is one product for one persona. The existing app targets the platform operator/builder — epics, backlog, portfolio, approvals — and the May 2026 audit deliberately narrowed its first release further to Paused-Work HITL approvals. That is a real and useful product. It is not what this goal asks for.

You are asking for a second product line: archetype end-user apps — the org's customers and its field employees — and you've already named the key insight: "all can use the same app, predicated on their persona and use case." That is exactly right, and the substrate to do it (archetypes, roles, work items, customer estate, dynamic rendering) is already in the schema.

The three real gaps — none of them "the basics":
  1. Connectivity / discovery. One app-store binary must reach N self-hosted single-org installs. Today the server URL is hard-coded at build time (EXPO_PUBLIC_API_URL), so the app reaches exactly one install. This is the routing problem you flagged.
  2. Persona-driven runtime UX. The app's tabs are static and operator-only. We need a manifest the install returns at login that drives which mode (customer / field / operator) and which screens the user sees — so one binary serves every archetype and persona.
  3. Native build & release. iOS binaries cannot be built in our Linux Build Studio (or any Linux box) — they need macOS + Xcode. We stand up EAS (Expo's cloud) to compile and ship, and you complete the store/account steps no agent can.

Bottom line: we are one product (operator companion) in; we add two persona modes (customer, field) on the same shell, solve discovery once, and stand up the cloud build pipeline. The heavy lifting is integration and one keystone abstraction — not greenfield.

3 · Keystone architecture — one binary, persona-routed

The whole design hinges on one move: the app is generic; the install tells it who the user is and what to show. After the user connects to their org's install and signs in, the app fetches a persona manifest — a small JSON document that declares the principal's kind, the org's archetype(s), the enabled modules/capabilities, the tab set, vocabulary overrides, and branding tokens. The shell renders entirely from that manifest plus the existing dynamic form/view renderer. No per-archetype app code ships in the binary.

Identity is already converged for this. AGENTS §11 (principal convergence) makes User, CustomerContact, Agent, and MobileDevice all resolve onto a single Principal; the alias kind tells the platform which surface authenticated. The manifest resolves on the Principal — so customer, employee, and operator are one identity model, three views.

The manifest (new contract — illustrative shape)

// GET /api/v1/app/config  → returned after login, drives the whole shell
{
  "principalKind": "customer" | "employee" | "operator",
  "org": { "name": "Acme HVAC", "archetype": "trades-maintenance/hvac-contractor" },
  "mode": "field",                 // which shared-shell mode to mount
  "tabs": ["jobs", "schedule", "customers", "more"],
  "capabilities": ["work-items", "offline-sync", "photo-capture", "signature"],
  "vocabulary": { "customer": "customer" },   // archetype overrides (e.g. "patient", "member")
  "branding": { "accent": "#1e6f50", "logoUrl": "…" }
}

This composes existing platform logic rather than inventing it: BusinessModelRole / platformRole (persona), StorefrontArchetype.activationProfile (modules + axes), getShellNavSections + portal-navigation-model.ts (nav resolution), resolveVocabularyKey (vocabulary), Organization branding.

4 · Repo & CI strategy — keep the monorepo, decouple the lane

Recommendation: keep mobile in the monorepo; do not split it out now. Mobile already consumes @dpf/api-client, @dpf/types, and @dpf/validators as workspace:*. A separate repo forces publishing and version-pinning those packages, which introduces contract drift between the API and its client and slows iteration — the opposite of the goal. The shared, always-in-sync API contract is the single biggest asset of co-location.

The "PRs take forever" pain is not caused by mobile being present. It's the apps/web four-shard vitest matrix plus the Next.js production build (15–20 min). Mobile changes neither need nor should wait on those. The fix is lane decoupling, not repo splitting:

  • Path-filtered mobile CI lane. A workflow that triggers only on apps/mobile/** + the three shared packages, running mobile typecheck + jest only. Web shards skip when a PR touches only mobile, and vice-versa.
  • Native builds off the PR gate entirely. EAS cloud builds run on merge-to-main / tag / manual dispatch — never blocking a PR. (iOS builds take many minutes on cloud macOS; they have no business in the inner loop.)

When to revisit a split: only if a dedicated mobile team with an independent release train emerges. Even then, prefer a published-contract package over a fork, so the API and client stay versioned together.

5 · Build & simulation — dev tools, cross-compile, and the iOS constraint

Hard constraint: iOS binaries can only be built on macOS + Xcode. No Linux cross-compiler exists. Our Build Studio sandbox is node:24-alpine (Linux), so it can never build iOS — and it doesn't build Android today either (no Android SDK / Gradle / Java).

The answer is to split "write & test code" from "compile native binary."

  • Code generation + unit tests (jest, typecheck): Build Studio, Claude, or Codex — all Linux, all fine. Build Studio stays viable for authoring and testing RN code; it simply does not compile the binary.
  • Native compilation (.ipa / .aab): EAS Build (Expo's cloud) runs macOS builders for iOS and Linux builders for Android. You do not need to own a Mac fleet for CI. A local Mac + Xcode is optional, only for deep local iOS debugging.
  • Store submission: EAS Submit → TestFlight and Play.

6 · Org-install connectivity — the hard problem, solved in phases

DPF is single-org-per-install on the customer's hardware, each with its own PUBLIC_URL and no central tenancy. A single app-store binary therefore can't "just know" where to connect. This is a solved pattern in self-hosted software — Mastodon, Nextcloud, Home Assistant, WordPress, and GitLab all ship one app and ask the user to point it at their instance, validated by a discovery endpoint. We adopt the same model.

8 · Testing strategy — without a phone lab

Your worry — "how do we test with lots of manual setup if real phones are used" — is handled by a layered approach where physical devices cover only what simulators provably can't.

LayerToolDevice neededIn CI?
Unit / componentjest + React Native Testing Library (exists)noneyes
E2E happy pathsMaestro flows (exist) on Android Emulatornone (emulator)yes
Real-device smokeEAS internal build → TestFlight (iOS) + Play internal (Android)1 iPhone + 1 Androidon demand
Device-matrix coverageFirebase Test Lab / BrowserStack / AWS Device Farm; Maestro Cloudnone (rented)scheduled

Kill the manual-setup tax with a seeded demo org. Ship a demo install + demo login + QR connect so a tester goes install → scan → signed-in in seconds, against throwaway demo data generated from the archetype seed per persona. Physical devices are then reserved for the four things simulators can't fake: push delivery, biometrics, real universal/app links, and store review.

10 · Research & benchmarking

  • Self-hosted multi-instance clients (Mastodon, Nextcloud, Home Assistant, WordPress, GitLab): one app-store binary + user-entered instance URL + discovery endpoint. Adopted: instance-URL entry + .well-known descriptor. Rejected as default: per-org white-label builds (store overhead, cost) — offered only later as a premium.
  • Field-service apps (ServiceTitan, Jobber, Housecall Pro, FieldEdge): convergent field-tech feature set — job list, schedule, "on my way", check-in/out, line items, photos, signature, offline. Validates our WorkItem/WorkSchedule + dynamic camera/signature surface; offline-first is table stakes.
  • Customer booking apps (Mindbody, Fresha, Square Appointments, Calendly): book, reminders, rebook, pay, membership. Validates StorefrontItem booking schema + Invoice/Payment reuse.
  • Mobile toolchain: Expo + EAS is the current industry-standard managed RN pipeline (cloud iOS builds without a Mac fleet). Already chosen in apps/mobile — keep.
  • Anti-pattern rejected: "the whole portal on a phone" (the May 2026 audit's own warning). We render persona-scoped surfaces, never a shrunk desktop.

13 · Decisions for you (I'll proceed on the recommended default unless you redirect)

A · Distribution model

Recommended: one generic app + instance URL

One DPF app + connect-to-your-org (Mastodon model, lowest cost) now; design so per-org white-label is a later premium. Alternative: white-label per org (expensive store overhead).

B · First persona mode after the manifest

Recommended: Field mode first

Field service is more defensible/sticky, reuses the WorkItem substrate, and avoids the payment/compliance entanglements of customer pay. Then Customer mode (broadest market). Your go-to-market may flip this — your call.

C · Repo

Recommended: keep monorepo + path-filtered CI

Split only if a dedicated mobile team with an independent release train appears; even then prefer a published-contract package over a fork.

14 · Out of scope

  • AI-coworker phone UI — coworkers are not phone users.
  • Multi-tenant SaaS — single-org-per-install stands; the discovery directory is a phonebook, not tenancy.
  • Tablet-optimized layouts — v1 is phone-first.
  • White-label per-org builds — deferred to a premium tier (design leaves room).
  • "The whole portal on a phone" — persona-scoped surfaces only.
