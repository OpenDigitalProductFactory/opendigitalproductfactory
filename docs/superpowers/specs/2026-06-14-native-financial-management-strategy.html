1. Decision

The operator directive (2026-06-14): "build the functionality that is equivalent to QuickBooks, not interface to it. That will be a deferred functionality as the cohesion of this system in one will be the compelling reason to lure customers away from it. If there is a gap in functionality, we close it."

DPF builds native financial management equivalent to QuickBooks. The QuickBooks integration becomes a migration bridge (import-from-QB, optional sync during transition), not the system of record. The end state: a switcher loses no accounting capability (we close every gap) and gains cohesion they cannot get from QB.

2. The cohesion thesis (why native beats integration)

An SMB field-service business today runs QuickBooks (accounting) + a dispatch tool (ServiceTitan/Housecall) + an inventory tool + spreadsheets, stitched by brittle integrations that drift. The win is not "better accounting than QuickBooks" — QB is mature. The win is accounting fused with operations and AI on one data model:

  • The invoice is not a synced copy — it is the close of the job that the same system dispatched, drew parts for, and warranty-classified.
  • A covered compressor part is $0 on the invoice because the same system holds the equipment's warranty terms — no re-keying, no integration.
  • The AI coworker sees the whole chain in one place — job → part used → warranty → invoice → payment → reorder — and watches every seam (the un-invoiced completion, the unpaid invoice, the margin leak). QuickBooks is accounting-only; it structurally cannot see the operation.

The moat is the loop, not the ledger. Two products integrated will always be two products. One cohesive system, with AI that reasons across operations and finance, is the reason to leave QuickBooks.

4. The gap to QuickBooks-equivalence (what to build)

DPF is a strong subledger + reporting system today — but not a double-entry accounting system. The keystone gap is the general ledger; it unlocks most of the rest. (Audit 2026-06-14: ~6–9 months to QuickBooks-Desktop parity, with a subledger→GL posting refactor.)

5. Migration bridge (how a QuickBooks shop switches)

The existing QB read client + erpSync fields are repurposed: import the customer's chart of accounts, open balances, customers/vendors, and history from QuickBooks into the native GL; optionally sync during a transition window; then cut over. The customer's accountant gets native statements + the year-end export. DPF never re-enrolls as a QB partner — it reads the customer's own QB via their connection (conduit).

6. SysML model

package NativeFinancialManagement {

  requirement def RF1_NativeLedger     { doc /* double-entry GL + chart of accounts; every financial event posts balanced entries */ }
  requirement def RF2_NativeStatements { doc /* P&L, balance sheet, cash flow computed from the GL, no QuickBooks dependency */ }
  requirement def RF3_BankRecon       { doc /* import bank/card txns; match + reconcile against AR/AP/payments */ }
  requirement def RF4_SalesTax        { doc /* compute tax by jurisdiction on invoices; period liability + filing support */ }
  requirement def RF5_Cohesion        { doc /* finance posts from operations (job/invoice/part/warranty/payment) on one model; AI reasons across both */ }
  constraint def  CF1_MigrationBridge { /* QuickBooks is import/sync-only during transition, never the system of record */ }
  constraint def  CF2_ConduitForRegulatedMoney { /* payroll / banking money-movement via the customer's own account (conduit), not DPF-as-partner */ }

  part def GeneralLedger    { // chart of accounts + journal entries (debit/credit), the gap to build }
  part def ARLedger         { // existing Invoice / InvoiceLineItem / PaymentAllocation -> posts to GL }
  part def APLedger         { // existing Bill / PurchaseOrder / Supplier -> posts to GL }
  part def FinancialStatements { // projections over the GL (P&L / BS / CF) }
  part def BankReconciliation { }
  part def QuickBooksBridge  { // import + optional sync; existing QB read client + erpSync fields }

  connection arToLedger connect ARLedger to GeneralLedger;   // field-service invoice (warranty-classified) posts here
  connection apToLedger connect APLedger to GeneralLedger;

  allocation f1 allocate ARLedger to existing.invoiceSubstrate;     // have
  allocation f2 allocate APLedger to existing.billPurchaseOrder;     // have
  allocation f3 allocate QuickBooksBridge to integrate.quickbooks; // repurpose as bridge
  // GeneralLedger, FinancialStatements, BankReconciliation: TO BUILD (deferred)

  satisfy RF1 by GeneralLedger;  satisfy RF2 by FinancialStatements;
  satisfy RF3 by BankReconciliation;  satisfy RF5 by arToLedger;
}

7. Deferred sequencing

  1. Now (in the dispatcher wedge): native field-service invoice → DPF AR (warranty-classified, F12/F14) + payment collection. No QuickBooks write. The warranty engine is already built/verified.
  2. Phase N1 — the ledger: chart of accounts + double-entry GL; AR/AP post to it. The keystone.
  3. Phase N2 — statements: build the balance sheet + trial balance from the GL; re-base the existing P&L / cash flow onto it (they work from subledgers today). Roll FixedAsset into the balance sheet.
  4. Phase N3 — live bank feeds (the reconciliation engine exists; add Plaid/API) + sales-tax filing execution (computation + liability tracking exist).
  5. Phase N4 — migration: QuickBooks import (chart of accounts, balances, history) + year-end/1099 export; cut-over.

This is a deferred, multi-phase build — captured as direction now. The dispatcher wedge proceeds on native AR; the GL and statements are the larger investment that makes the "replace QuickBooks" claim real.
