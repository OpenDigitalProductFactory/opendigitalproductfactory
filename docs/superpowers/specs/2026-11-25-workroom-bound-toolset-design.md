# Workroom-bound toolsets for AI coworkers

**Backlog item:** BI-687E7D81 · **Workroom:** WC-EA8680B0 · **Epic:** EP-INPLATFORM-CODING
**Parent:** [T3 Code absorption, S5](2026-11-13-t3-code-absorption-design.md) and M2 of BI-3E2B7A96.

A Workroom can admit a coworker to perform one job at one stage without granting it all the tools the room, its owner, or the provider can use. The 2026-11-24 owner amendment makes identity and qualification inputs to that decision. T3 supplies threads, provider turns, redirects, and capacity. DPF composes and authorizes the toolset. The DPF2 launcher consumes it and cannot widen it.

## Objectives

**OBJ-S5-REGISTRY:** Make operational access a required declaration for every MCP registry entry, including a deny-by-default path for dynamic tools.

**OBJ-S5-AUTHORITY:** Bind the session to its coworker, assigned job, explicit authority, Workroom and stage, and enforce the intersection when an operation starts.

**OBJ-S5-BOUNDARY:** Enable bounded source work, verification, evidence and PR operations without a general shell or access outside the room's authorized source and resources.

**OBJ-S5-LIFECYCLE:** Revoke a released session without a client callback and prevent a stale session from recovering authority across a stage change, membership change, or restart.

**OBJ-S5-HOOKS:** Transfer each hook guarantee to its named owner and require hook-free evidence before retiring any covered external hook path.

## Research & benchmarking

| Reference | What transfers to DPF and what does not |
| --- | --- |
| Open source · [OpenFGA task-based authorization](https://openfga.dev/docs/modeling/agents/task-based-authorization) | The model relates task, agent, tool and resource separately and applies conditions and intersections at check time. Adopt those independent checks. Do not mirror Workroom participants and grants into relationship tuples in a second store. |
| Open source · [Cedar request and entity model](https://docs.cedarpolicy.com/overview/terminology.html) | Separate principal, action, resource and request context, with deny as the baseline. Adopt typed decision inputs and explicit default deny. Keep DPF's existing TAK/Workroom policy engine and grant data rather than adding a policy language. |
| Open source · [BMAD evaluation](../../security/tool-evaluations/2026-09-15-bmad-method.md) | Adopt explicit stage deliverables and a handoff boundary. Prompt/workflow roles alone do not protect a resource when the model or hook is absent. Retain Workroom stage authority, not BMAD as an executor or dependency. |
| Commercial · [AWS IAM session policies](https://docs.aws.amazon.com/IAM/latest/UserGuide/access_policies.html#policies_session) | The session restriction is an intersection with underlying permissions. Adopt the non-expanding ceiling. Do not use generic cloud policy documents as DPF job records. |
| Commercial · [GitHub App installation access tokens](https://docs.github.com/en/apps/creating-github-apps/authenticating-with-a-github-app/generating-an-installation-access-token-for-a-github-app) | The issued token can restrict both repositories and permissions relative to the installation. Adopt independently bounded target and operation. Do not give the provider an installation token or treat expiry as a release signal. |

Follow [NIST SP 800-162](https://csrc.nist.gov/pubs/sp/800/162/upd2/final) for the subject/action/object/context distinction. Follow [MCP authorization](https://modelcontextprotocol.io/specification/2025-11-25/basic/authorization) on audience and no upstream token passthrough. [RFC 8693](https://www.rfc-editor.org/rfc/rfc8693.html) is a useful delegation comparison, not a new exchange endpoint. DPF already has an opaque, directly revocable first-party room credential. No dependency is added.

Reject a universal room-scoped token because the same room would give every job the same operational authority. Reject a launch-time allowlist without runtime revalidation because stage, participant and binding can change. Reject provider- or hook-owned authorization because neither has live Workroom and JSI state and neither is present on every path.

## DPF producer and DPF2 consumer

The producer takes an authenticated reference to a persisted Workroom stage assignment/admission. It resolves the executing coworker and sponsor separately and verifies active membership and the correct tenant on the server. Neither the launching user's identity nor T3's harness reference substitutes for the assigned coworker. The current job/activity and stage come from the assignment and declared Workroom shape, not the launch request, persona text, or role name supplied by the model.

1. Resolve the local canonical agent identifier and active Principal for this admitted participant. Use [`getAgentGaidMap(agentIds, db?)`](../../../apps/web/lib/identity/principal-linking.ts), unchanged, and refuse missing or inconsistent GAID. No new identity producer is needed. GAID identifies the subject, never permission. Keep the existing DPF2 launch slice compatible.
2. Read the existing job profile and grant substrate ([job profile design](2026-09-09-coworker-job-profile-personification-design.md), [tool grant design](2026-04-27-coworker-tool-grant-spec-design.md)). For [TAK-JSI](../../architecture/job-specific-intelligence.md), read the applicable job/activity, operating-profile version, deployment context, and data and risk restrictions, with issuer and valid/current evidence. A checked-in persona, self-reported role, grant, or test alone is not a qualification.
3. Resolve JSI and binding through the shared eligibility code. Pin an active explicit `AuthorityBinding` to the same current Principal, tenant and assigned job/shape scope. Carry the selected binding identity through execution. Use the existing `AuthorityBindingSubject` association and authority grants; do not aggregate unrelated people or shape-wide rows. If the current resolver needs an explicit scope descriptor or qualification evidence input, extend it in place without changing coordination's proven semantics. Never add a parallel check.
4. Use the current [Workroom participant action fence](../../../apps/web/lib/work-management/workroom-agent-access.server.ts), declared stage and current dispatch/attempt identity. Stage name alone is insufficient when a room returns to the same stage. Resolve scope claims from their persisted current release epochs when the operation needs them.
5. Compose the issued surface from the assigned job's permitted operations ∩ applicable JSI ceiling ∩ explicit binding ∩ Workroom stage ∩ deployed registry ∩ existing token/coworker/human/tenant authority. Each operation must also fit the session's runtime ceiling and actual bound resource at invocation. Forwarding intersects with any narrower host/downstream constraint and cannot substitute another principal, job, room, worktree, or broader credential.

At this checkout the shared resolver detects candidate qualification models, but the schema has none of those models. No-source or read failure is not proof of qualification. Preserve DI-FF4A015CF917's `not-applicable` where no scheme is required and enable only explicitly authorized work under the applicable oversight. If the job or operation requires JSI, absent/unavailable current evidence means hold or narrow to separately admitted work that does not require that qualification. No production claim of AC-5 qualification coverage based on fixtures, a fabricated row, or a no-scheme run. BI-6DB95601 covers the related activation/revalidation interlock, not proof of an available qualification-record writer. The plan must verify the owning lifecycle producer or file an exact uncovered dependency before carrying the qualified pilot into production.

For example, an engineer and a coordination specialist can participate during the same room stage. The engineer's assigned activity, explicit binding and qualification may allow a worktree edit and scoped test but no staffing action. The specialist's route-and-handoff activity may allow room/route operations but not a source mutation. Common room messaging can appear in both surfaces when authorized by the stage and membership, including the bound room message resource from S5. There is no `if coordinator then deny writes` branch. A room message and a source mutation have different target and effect, even if both have a write side effect.

DPF provides a versioned, server-verified launch projection with session ref, admitted GAID, Workroom/stage attempt, bound worktree/host ref, runtime mode, and permitted operation names. DPF separately delivers the opaque room token over the existing secure provider connection at launch. The non-secret projection is not a bearer credential and is never accepted as an authorization input. DPF2 presents only the operations that its trusted host can mediate for the exact admitted attempt. This does not require a provider-native MCP connection. It must fail closed if it cannot apply the exact mode or source boundary, and keep producer-issued identity opaque to T3. No DPF2 or T3 source change is in the DPF producer PR. BI-B62B218E supplies external session admission/staffing; BI-5A866218 supplies execution-host identity and narrowing. Their joined-path proof is a release dependency, not a reason to implement those engines in S5.

## Server enforcement and lifecycle

- Require a DPF-owned `McpToolAccess` declaration with explicit operation semantics (source read, source edit, scoped test, gate, evidence, publication, room operation, or outside the Workroom-session boundary). Grant allowlists use actual registered names. A mixed-action tool must declare its most privileged class unless it uses a validated per-action classifier that refuses unknown actions. Dynamic tools use DPF-owned approved metadata; missing or unknown access cannot be listed or dispatched. Scope and token level remain separate; registry tests cover packs, aliases, dynamic intake and special protocol branches. Missing declaration on a static entry is a TypeScript/build error, not just a lint warning.
- Define named runtime modes with explicit permitted operation classes, not a new hierarchy of OAuth scopes. The default coding mode can accommodate the AC-3 classes, but the job/stage may expose fewer tools. A classified privileged tool or any general command runner is outside this mode. Unknown modes/classes fail closed. Keep a typed access declaration shared by listing and execution rather than another list embedded in an adapter.
- Reuse the existing `McpApiToken` row and binding/resource fields. Add only the versioned session-bound data not represented there: exact admitted session/stage attempt, principal/job/qualification references, maximum mode, and the issued tool projection. The projection is a non-expanding authorization snapshot, not a copy of qualification or membership truth. Validate on read; no malformed, unbound, or old broad token can be interpreted as a governed token. Store no bearer plaintext, provider secret, or policy prose in the projection or audit. Preserve existing credential-retention classification and audit behavior. Implementation needs a data-reviewed migration/convergence plan for the exact carrier.
- List/discover and invoke using the same live authorization intersection. Check explicit and implicit resource references after canonical resolution, including nested inputs, opaque task/resource/subscription IDs, derived targets, and path/host/source refs. Refuse tools with no complete typed target adapter. Preserve existing grant, sensitivity, business-consequence and action-specific approval checks. An owner approval does not widen an old token: only a new, separately approved, bounded action/session can do work outside the issued envelope.
- Enforce before handler/effect admission, not only in the launch response or MCP listing. Apply equivalent checks to `tools/call`, approved/deferred replay and any enabled tasks/resources and native broker path. Bind a `resources/read` or subscription to the specific room with the same fence; fan-out must terminate or suppress delivery on lost authority. Disable methods or routes until they can enforce it. Durable effects recheck immediately before becoming irreversible. Serialize effect admission with membership/stage/binding/release updates or use the existing durable compare-and-fence identity. Define the linearization point in tests: a denied or fenced operation never starts, and already-started work is interrupted/reconciled without claiming an external effect was undone.
- Release fences the exact session synchronously and revokes its credential. Existing durable supervisor effects repeat revocation on restart and handle termination, failed launch, handover and room close. A concurrent sibling is unaffected unless the room itself closes. Old tokens cannot gain tools if the live grant grows, and a stage round trip or remove/re-admit cannot reactivate an old token. Re-issue for a new authorized attempt. Refreshing idle expiry must not undo a release or bypass delegated lifetime.
- The model has no general shell, generic test command, arbitrary connectors, operator secrets, Git/host admin credentials, or inherited broad filesystem/network access. The trusted execution broker provides repository tools, edits confined to the canonical admitted worktree and scope, fixed named checks in an isolated runner, and PR/gate operations via governed services. Tests execute mutable code, so their environment has only the necessary files/scratch, no host credentials or shared sockets, and controlled egress. The launcher is an enforcement point for native capability exposure, not a policy source. A supported mode must control native execution independently of a prompt or provider request callback, or it is not supported for this rollout.

This extends deployment [contracts 3, 4, 6, 8, 9, 10 and 11](2026-05-09-deployment-contracts.md): revocable lifecycle, canonical identity, governed runner, secret delivery, provider routing, MCP boundary and delegated coordination. Reads are keyed to one token, member, binding, active stage and assigned qualification, using indexed identities. Release uses the exact token ID and the existing room/revocation index. Composition is linear in the bounded enabled registry, not installations or coworkers. Calls check only the invoked operation and indexed live facts. First slice serves one installation and its registered execution hosts, with no federated policy fan-out. Scale release requires measurements at the configured host admission limit with concurrent sibling sessions and no room-wide scan per request. EP-INPLATFORM-CODING, particularly BI-5A866218 and BI-B62B218E, covers extension beyond the first host; growth of a local catalog does not justify skipping authority checks.
