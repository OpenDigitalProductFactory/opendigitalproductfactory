1. Problem — model selection is split across three sources with no synthesis

A "local-model" Build Studio campaign actually ran on cloud — nobody noticed until the GPU sat idle. The cause is structural: which model/provider/engine executes a build phase is decided in three places that nothing reconciles, and no view or tool resolves the effective per-phase answer before a run.

#Config sourceAdmin surfaceGoverns
1V2 routing (routeAndCall → routeEndpointV2)Providers & Routing (/platform/ai/providers)Every routed phase: plan, design-review, plan-review, ideate-when-opencode, build-when-not-opencode
2Build dispatch engine (getBuildStudioConfig().provider, PlatformConfig["build-studio-dispatch"])Build Runtime (/platform/ai/build-studio)The ideate engine and the build engine (only opencode makes build local)
3Served context window (preflightLocalEndpoint → /v1/models)none — invisible to both pagesWhether the local model can actually run an agent loop (≥ OPENCODE_MIN_CONTEXT_TOKENS)

The decisive mechanism is Stage-5b of routeEndpointV2 (apps/web/lib/routing/pipeline-v2.ts): a stable sort puts user_configured (cloud) endpoints ahead of bundled (local) ones. So on a mixed install a routed phase picks cloud even when a local model is available and free. Selecting "Local model (OpenCode)" in Build Runtime makes only the build phase local; ideate, plan, and both reviews still route to cloud.

3. The SysML v2 model

The build lifecycle's model-selection allocation in SysML v2 textual notation — phase actions allocated to the dispatch-mechanism parts that realize them, each part allocated to its governing config source and its as-built code, with the tier-sort recorded as a constraint:

package ModelSelectionAsBuilt {

  // ---- Requirements (what the runtime-health layer must guarantee) ----
  requirement def R1_OneAuthoritativeView {
    doc /* An operator OR an agent resolves, in one place, which
           provider/engine/model runs each phase right now. */
  }
  requirement def R2_PredictBeforeRun {
    doc /* The answer is available BEFORE a build runs, using the same
           routing logic the build uses (no drift). */
  }
  requirement def R3_FlagContradictions {
    doc /* Where live config contradicts platform guidance is flagged:
           local-intent-but-cloud-reasoning, context-below-floor,
           embedding-model-first. */
  }

  // ---- Config sources (the three split authorities) ----
  part def ProvidersAndRouting;   // V2 routing — /platform/ai/providers
  part def BuildRuntime;          // dispatch engine — /platform/ai/build-studio
  part def DmrServingConfig;      // served context window — no admin surface

  // ---- Dispatch mechanisms (how a phase actually reaches a model) ----
  part def RoutedDispatch;        // routeAndCall -> routeEndpointV2
  part def VendorCliDispatch;     // claude/codex/grok CLI in the sandbox
  part def LocalOpencodeDispatch;  // opencode CLI against the local endpoint

  // ---- The blind-spot constraint: tier-sort dominates ranking ----
  constraint def C1_TierSortPrefersCloud {
    doc /* routeEndpointV2 Stage-5b stable-sorts user_configured ahead of
           bundled, so a routed phase picks cloud over an available local
           model on a mixed install. pipeline-v2.ts. */
  }

  // ---- Phase actions, allocated to the mechanism that realizes them ----
  action def Ideate;        allocate Ideate      to RoutedDispatch, VendorCliDispatch;
  action def Plan;          allocate Plan        to RoutedDispatch;
  action def DesignReview;  allocate DesignReview to RoutedDispatch;
  action def PlanReview;    allocate PlanReview  to RoutedDispatch;
  action def Build;         allocate Build       to LocalOpencodeDispatch, RoutedDispatch;

  // ---- Mechanism -> governing source, and the tier-sort it inherits ----
  allocate RoutedDispatch       to ProvidersAndRouting;
  allocate VendorCliDispatch    to BuildRuntime;
  allocate LocalOpencodeDispatch to BuildRuntime, DmrServingConfig;
  satisfy C1_TierSortPrefersCloud by RoutedDispatch;

  // ---- As-built code allocations (the projection's authority) ----
  allocate RoutedDispatch to
    "apps/web/lib/inference/routed-inference.ts#routeAndCall",
    "apps/web/lib/routing/pipeline-v2.ts#routeEndpointV2";
  allocate VendorCliDispatch to
    "apps/web/lib/integrate/ideate-dispatch.ts#dispatchIdeateResearch";
  allocate LocalOpencodeDispatch to
    "apps/web/lib/integrate/build-pipeline.ts#stepGenerateCode",
    "apps/web/lib/integrate/opencode-dispatch.ts#preflightLocalEndpoint";

  // ---- The runtime-health layer that resolves + flags all of the above ----
  action def ResolveModelSelection;  // one resolver, three surfaces
  verification def V_PredictionMatchesRun {
    doc /* previewRoute (a side-effect-free dry-run of routeEndpointV2)
           predicts the per-phase winner; verified to match what actually
           ran by driving a build on the live install. */
  }
  verify R2_PredictBeforeRun by V_PredictionMatchesRun;

  allocate ResolveModelSelection to
    "apps/web/lib/inference/phase-model-resolution.ts#resolveModelSelectionByPhase",
    "apps/web/lib/inference/routed-inference.ts#previewRoute",
    "apps/web/lib/mcp-tools.ts#resolve_model_selection",
    "apps/web/app/(shell)/platform/ai/runtime-health/page.tsx";
  satisfy R1_OneAuthoritativeView by ResolveModelSelection;
  satisfy R3_FlagContradictions   by ResolveModelSelection;
}

4. How the gap is closed — one resolver, three surfaces

A single resolver, apps/web/lib/inference/phase-model-resolution.ts#resolveModelSelectionByPhase, computes the per-phase allocation above and the contradiction flags. It reuses the real routing logic via previewRoute() (routed-inference.ts) — extracted from routeAndCall so the prediction runs the identical routeEndpointV2 the build uses, with skipRecipe to stay deterministic and side-effect-free (no dispatch, no challenger roll, no persisted decision).

  • Operator → the /platform/ai/runtime-health page: a verdict (all-local / all-cloud / mixed / unconfigured), a per-phase table (runs-on, provider/model, mechanism, governed-by, context), and a Mismatches & remediation list.
  • Agent → the resolve_model_selection MCP tool: the same overview as structured data, so a coworker establishes ground truth in one call before driving a build.
  • Architecture → this projection: the as-built dispatch/routing allocation the Parity Engine (EP-PARITY-ENGINE) had no source for.

5. Contradiction flags (realized)

CodeSeverityFires when
local-intent-cloud-reasoningerrorBuild engine = opencode but a reasoning phase (ideate/plan/design-review/plan-review) resolves to a cloud provider — the headline blind spot.
context-too-smallerrorThe local endpoint reports a served context below OPENCODE_MIN_CONTEXT_TOKENS (e.g. qwen3-coder at 4096 vs the 22k floor).
embedding-model-firstwarningThe local /v1/models list leads with a non-chat model (isLikelyNonChatModel), risking an embedding model being picked for code-gen.
build-engine-not-appliedinfoA claude/codex/grok build engine is selected, but the build phase still routes through the agentic loop — the CLI choice only governs ideate.
ideate-opencode-routesinfoIdeate runs through routing even under the local engine (it does not invoke the local runner directly).

6. Verification

  • Pure unit tests for the resolver (apps/web/lib/inference/phase-model-resolution.test.ts): local-but-cloud-reasoning flags on every routed phase, context-below-floor, embedding-first, all-local clean, all-cloud + build-engine-not-applied, agentic-ideate-unsupported, no-providers → unconfigured.
  • Existing routing suites (pipeline-v2.test.ts) confirm the previewRoute/skipRecipe extraction did not change routing behavior.
  • Live functional verification (V_PredictionMatchesRun): drive a build on the live install and confirm the predicted per-phase provider/model matches what actually ran — closing structural-verification-is-not-functional.
