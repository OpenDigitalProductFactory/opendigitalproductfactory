# Preserve candidate-promoter failure diagnostics

BI-FE0259A7; WC-130C04BA. This is a small fix to the existing failure path,
grounded in [procedural verification §3.3](2026-06-06-procedural-functional-verification-design.md#33-faster-classified-failure-handling-so-the-stop-rule-is-cheap-not-lossy).

## Reproduction and research

SUR-B0A4610D failed before drain on November 11 at 22:37 UTC. The owner UI and
native stored failure retain the Dockerfile package-install command and exit9,
but no primary APK error. The underlying package/network cause is unknown.
At source `8046e0d0082153e1219d57bba989e48c63012632`,
`apps/web/lib/self-upgrade/promoter-artifact.ts` selects stderr OR stdout and
keeps only its final500 characters. Long Docker summaries can erase the causal
line, and nonempty stderr can erase useful stdout. Staging cleanup is correct.

Graph-linked tests resolve to `promoter.test.ts` and
`diagnostic-evidence-redaction.test.ts`. The existing shared diagnostic redactor
already excludes known token/image patterns; extend that policy for assignment
and URL credentials before retaining more output. Readiness keeps its own short
summary; the existing run failure log carries the bounded diagnostic. No new
store, API, renderer or classifier is required.

Rejected: merely increasing the final-tail length (still loses other stream and
leading errors); saving unbounded raw output; rebuilding production to recover a
lost log; guessing APK cause from exit9. Synthetic regression fixtures will be
labelled as such and cannot establish the production package failure's cause.

## Contract and flow

C-DIAGNOSTIC: Docker failure output is evidence, not an authoritative cause
classification. Bound the retained error to at most 12,000 output characters
plus fixed operation/status labels. Reserve space inside that budget for the
existing network-cause summary, then divide the remainder between present streams;
retain each stream's beginning and end with an explicit omission marker.
Redact before slicing so a cut cannot expose part of a recognized credential.
The redactor is pattern-based and does not promise detection of arbitrary secrets.

F-FAILURE: existing runner result → shared redaction → bounded stream excerpts →
existing thrown failure → readiness/run failure record → existing owner/MCP
readers. No command arguments, environment dump or credentials are added.
Success returns the original stdout untouched for image/contract parsing.
The cause summary and retry warnings use the same credential redactor before
truncation. This preserves interior network causes without retaining raw secrets.

## Boundaries, risk and rollback

No migration or wire-schema change. Existing source/digest validation and
upgrade authority remain unchanged. No package/mirror/network policy, host
maintenance, image retag/manual build, retry-policy, access/provider/budget change or
offline-restoration privilege is included. The production APK cause stays unknown.

More output increases disclosure risk; redact before bounding and test streams
independently. Generic credential assignments can over-redact diagnostic prose;
retain ordinary structured evidence in shared-policy controls. Truncation can
still omit an interior cause, so mark it and never call an excerpt a full log.
Revert this one diagnostic repair through normal protected delivery if needed.
