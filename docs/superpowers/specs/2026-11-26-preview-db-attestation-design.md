# Attest the database of a leased Contributor preview

BI-5C193A3F. First in the S5 preview dependency stack. This change supplies read-only proof, not enrollment, draft provisioning or activation.

**OBJ-1:** The lease owner can attest the exact dedicated database used by the current Contributor preview, and the consumer can match it on the transaction that would write.

| Acceptance | Objective | Statement |
| --- | --- | --- |
| AC-1 | OBJ-1 | A current lease owner records the database identity from the dedicated preview, bound to the exact lease, runtime and source revision. |
| AC-2 | OBJ-1 | The transaction rejects a different cluster with an identically named database, a different database on the same cluster, unreadable proof, or missing, expired, revoked or replaced owner provenance. |
| AC-3 | OBJ-1 | Production and unattested installations cannot use the proof as authorization. No agent, host-runner or Docker read of the production database, no production credential handling, and no new privileged role. Only the portal's existing connection reads its own control identity. |

## Design

The authenticated lease owner reuses the existing TaskRun binding in `environment-lease-provenance.ts`. The host adapter in `scripts/lib/dev-preview-runtime.mjs` already uses Docker inspect and exec. Extend it to inspect the exact dev-postgres container and its mounted Compose `dev_pgdata` volume, then execute a read-only PostgreSQL catalog probe inside that container over its local socket as the existing PostgreSQL 16 `dpf` bootstrap superuser. Never use the consumer's DSN. Bind the inspected container ID, exact volume name, lease and immutable runtime/source revision to the resulting tuple. The existing check for the hostname dev-postgres is only a configuration check. The live-DB override demonstrates why it cannot establish the consumer connection.

Inside the owner transaction that publishes the proof to TaskRun, the production portal process reads `SELECT system_identifier::text FROM pg_catalog.pg_control_system()` on its own existing connection. That transaction also reads the lease row, so its connection identifies the lease-owning cluster by construction. A permission error on `pg_catalog.pg_control_system()` counts as a missing identifier and holds. Never remedy it by granting access. Reject missing or equal production and preview identifiers before publishing even if all other metadata matches. The consumer independently rejects missing identifiers or equality. Cluster identity matters because both installations may name the database dpf and have the same catalog OID. The host adapter probes only dev-postgres. No agent, host runner or Docker exec reads the production database. Test the portal publication path exclusively against disposable PostgreSQL and never exercise it against the live install.

Use the sanitized-clone readback pattern with PostgreSQL's system identifier, current database OID and name, and postmaster start time. Fully qualify catalog relations and calls, including `pg_catalog.pg_control_system()`, `pg_catalog.current_database()` and `pg_catalog.pg_postmaster_start_time()`. Use one shared probe serialization contract for owner and consumer: `system_identifier::text`, decimal OID text, datname, and `extract(epoch from pg_catalog.pg_postmaster_start_time())::numeric::text`. Do not use timestamptz text, JS Date or JS Number. Both paths use the same canonical SQL projection. A postmaster restart changes the time and an independently initialized replacement volume gets a new system identifier. Both invalidate the previous proof. Physical copies can preserve identifiers, so the tuple does not replace inspection of the dedicated runtime and storage. It establishes identity, not data freshness or unused contents. Restore fencing and one-shot accounting stay with BI-60FC9291 and BI-588688A7.

After the host probe, revalidate the exact active lease/runtime under the owner environment lock before publishing. Store the versioned proof only in `TaskRun.progressPayload.nonprodPreviewDatabaseAttestation`, with this layer as its sole writer. Merge into the current payload using a compare-and-set (CAS) conditioned on both the observed status and progressPayload. Publication is allowed only onto a completed wait with outcome admitted whose exact lease is still current. Current means the locked lease is active, its expiry is strictly after the same `now` used by renewal, and `previewWaitMatchesOwner` verifies the deterministic TaskRun and its stored owner provenance against the authenticated actor and lease binding. The TaskRun must be completed and its wait state admitted. A lapsed but not yet reaped active lease, including expiry equal to now, takes the lost-renewal path before renewal updates expiry. The publication tool independently refuses a lapsed lease on its own locked read. It samples the clock after acquiring the environment lock, like renewal, and never extends expiry. Expired, released, replaced and cancelled leases, stale or noncurrent lease identity, and non-admitted completion all refuse. On a CAS miss, re-read and re-evaluate the lease and wait before retrying. `waitPayload` spreads its input snapshot, but that alone does not protect the checkpoint upsert or non-expiry settle update against overwriting a concurrent publish. Change both existing-row writes to condition on the observed status and progressPayload, following the expiry settle CAS. Create a missing checkpoint separately and re-read on a concurrent create. On a missed CAS, re-read and re-evaluate the transition before a bounded retry, or return a retryable hold. If non-expiry settlement exhausts retries inside release, roll back the entire release and return the retryable `nonprod_release_wait_settlement_contended` error. Release is idempotent. Preserve sibling keys and prevent stale snapshots from deleting or restoring proof. Revalidate active owner and all lease/runtime bindings on every read. New admission must not copy old proof. Keep the existing `nonprodPreviewOwner.schemaVersion` at 1, owned by the lease provenance contract. BI-8EA98961 must not share this DB-proof version or overwrite this key.

Fetch the expected proof from the authenticated owner before opening the preview transaction. No network I/O under an owner lock or a preview write lock. The helper in `preview-db-attestation.ts` compares on the transaction-scoped client that would perform the write and refuses the root pooled client. Neither a cached lease read nor the comparison proves lease currency at commit. That requires BI-60FC9291. This layer cannot authorize a setup call or register a setup surface. Authorization unconditionally holds until BI-8EA98961 supplies its verified non-production installation join. An injected class flag is not supported.

## Host-to-owner channel

The host already uses authenticated MCP for the lease lifecycle. The [wrapper](../../../scripts/lib/dev-preview-runtime.mjs#L419) reads the admitted lease and [renews it after local inspection](../../../scripts/lib/dev-preview-runtime.mjs#L492). Its preview health request is a read of the preview, not a write to the owner. The [renewal schema](../../../apps/web/lib/mcp/packs/nonprod-lease-definitions.ts#L207) carries lease/session, slot and pressure data only. [Runtime target heartbeat](../../../apps/web/lib/mcp/packs/runtime-coordination-pack.ts#L65) carries a target ID, and [preview provenance](../../../apps/web/lib/nonprod/environment-lease-provenance.ts#L140) is written server-side at admission, before the host probe. None carries the proof as-is.

Use a separate governed `attest_preview_database` side-effect tool in the existing nonprod lease pack, with static `consequence: "authority"` and existing `work_capsule_write` grant. Do not add it to the quiescence-safe set. Only an explicit operator opt-in to S5 rehearsal preview mode enables the host to send one freshly inspected observation, after a successful renewal and outside the lease lock. Ordinary Contributor previews never call this tool or generate its approval card. This opt-in is launcher policy, not a server authorization control. This is acceptable because consumers require the verified BI-8EA98961 installation join as well as the proof. A lease without proof holds at every consumer. Ordinary renew stays unclassified, keeps its known-unclassified registry entry and quiescence allowance, and carries no observation field. External-jsonrpc decision routing defaults to shadow mode, which records the would-deny result without denying. Enforce mode refuses an unconsulted call before publication. The separate tool avoids burdening heartbeats because the governed execution, consequential tool policy, decision-routing and workroom-shape paths read static classification even when an approval refiner returns null.

S5 rehearsal preview mode requires the operator to have selected the `active-candidate` lane through the existing configuration and shared nonproduction lease process before launch. It never switches lanes itself. The ordinary and default lane stays `local-integration-ci` and is not an alias for the preview owner predicate. On any other lane the launcher emits `s5_preview_active_candidate_required`, names the missing precondition and exits before an MCP request. Selecting the lane for the actual rehearsal is an operator step at rehearsal time, outside this delivery.

Publication must go through its own governed authorization and any applicable approval. A refusal or pending approval does not block heartbeats, and the launcher must not bypass or repeatedly submit it. The new handler receives `(params, userId, context)` and uses authenticated user/agent values exactly as release does. Never use actor IDs from payload fields. A readable session ID alone proves no authority. The new tool validates the observation without I/O, then starts its own lease-owner transaction. Acquire the existing owner environment lock, sample time and re-read the exact active lease and owner TaskRun. Refuse unless the lease, ownership, admitted outcome, source/runtime, and strict future expiry checks all pass. A lost renewal must not lead the launcher to send an observation; loss, expiry or replacement between calls holds at the publication re-read. Publication neither renews nor changes expiry. If observation publication is refused, the earlier successful renewal is unaffected.

Use the launcher’s existing credential resolution without assuming an assistant, tier or steering identity. Under the normal tier-1 or tier-2 operator policy, an authority consequence requires an owner approval even when connection delegation steers the call. One approval per explicitly requested rehearsal observation is appropriate: this is a one-shot, owner-supervised rehearsal and the proof can authorize downstream effects. A credential or decision-routing refusal leaves the proof absent and does not stop ordinary renewals.

After owner approval, the existing `runApprovedExternalRequest` path replays the original bounded observation server-side through governed execution. The launcher does not resubmit. Send no taskRunId, routeContext or chainId with the attestation call. Also verify the actual authenticated context: the external route can attach task or route binding from the credential even when the request omits them. A task-bound context cannot use external approval replay and holds without publishing. At replay the handler repeats all checks under the owner lock, including the exact current lease and owner binding, strict expiry, admitted outcome, source/runtime binding and CAS against the current payload. The retained observation must remain bound to the still-current lease, runtime ID and source. For a different tuple, accept replacement only if its postmasterStartEpoch is strictly greater than the stored value, compared as exact decimal strings without JS Number. Otherwise give a typed stale-observation refusal with no write. An identical tuple is a no-op. A lapsed or replaced lease returns a typed refusal with no proof write. The portal does not independently verify Docker or physical database freshness from a delayed approval; the host observation remains a claim and the consumer still compares the live transaction identity before use.

After the locked checks, open a proof savepoint, read the lease-owning identifier on that transaction connection and CAS the proof. Once the savepoint is opened, ROLLBACK TO SAVEPOINT on every non-publishing exit, including permission denial and identical replay, and RELEASE SAVEPOINT only after successful CAS. A pre-savepoint refusal needs no rollback to savepoint. No network I/O under the owner lock.

The server derives the expected logical `runtimeId` as the canonical digest of the exact persisted `nonprodPreviewOwner.binding` assembled by `previewBinding(lease)`. Recompute it from the locked authoritative lease and require equality with both the stored binding and the submitted logical ID. This is not a Docker container ID. The source SHA is the claimant’s assertion captured in the lease at admission and immutable afterwards, not a server-derived revision. Match `sourceSha` to the single lowercase 40-hex SHA in the final parenthesized segment of the owner lease's recorded Contributor preview purpose, using the [existing admission format](../../../scripts/dev-portal-lease.sh#L309). Reject unparseable or ambiguous provenance rather than treating the host SHA as the expected value. The portal records `containerId`, `volumeName` and the database tuple as host-observed claims, not independently verified facts. The transaction comparison, installation join and setup reservation remain mandatory downstream.

### Observation and audit contract

The observation is an object with `schemaVersion: 1`, `leaseId` and `runtimeId` (up to 128 UTF-8 bytes each, nonempty), a lowercase 40-hex `sourceSha`, a lowercase 64-hex `containerId`, a nonempty `volumeName` of at most 128 UTF-8 bytes, and `database` with `systemIdentifier`, `databaseOid`, `databaseName` and `postmasterStartEpoch`. Reuse the comparison helper's string patterns for system identifier, OID and epoch. Require a nonempty database name of at most 63 UTF-8 bytes. Reject unknown properties at both object levels and serialized UTF-8 larger than 2048 bytes. Explicitly refuse a submitted `productionSystemIdentifier` at either level. Put the observation in the new tool’s definition, not renewal’s. An absent, null, array or other non-object observation returns typed `preview_database_observation_invalid` before proof I/O. The schema’s additionalProperties declaration is advisory; the server parser is authoritative for shape, unknown-key refusal and byte bounds. Return the typed parse refusal through the publication tool while leaving ordinary renewal untouched.

Put one structured disposition per proof publish or refusal in `ToolResult.data.previewDatabaseObservation` for the existing governed ToolExecution audit channel. The publication tool is a side effect so its default audit class is ledger, not metrics_only. `auditableResult` retains this data unless explicitly redacted, so keep the bounded disposition key. Send only the schema fields, preserving the specified string types through transport and coercion. Governed approval can park before the tool handler runs, so without an earlier schema validation hook the parked ledger and approval card depend on the launcher emitting only schema fields. The handler’s strict parser still refuses unknown fields before any proof effect. Retain the bounded observation arguments for replay fingerprint verification; do not mark them writeOnly. Lease/runtime/source/container identifiers, volume name and the dev-postgres system identifier, OID, database name and start epoch are non-secret identity values. The strict schema admits no password, credential, URL or production identifier. Record the lease, authenticated actor, reason code and bounded canonical tuple digest (null if unparseable), never raw connection details or credentials. An identical proof is a no-op. A different tuple may replace it only after fresh host inspection of container and volume and a new database probe. The host sends each new observation once, not on every heartbeat. The portal applies the locked checks even on replay and deduplicates exact repeats.

The new tool is refused by the governed drain gate, including the cleanup allowance that only lists existing safe tools. Before opening the savepoint, also read the canonical persisted `portal.quiescence` on the transaction connection. Refuse drain, swap or unreadable state so a request admitted before drain cannot land during it. Keep the ordinary heartbeat outside this path.

### Actual Contributor preview claim shape

The current [launcher](../../../scripts/dev-portal-lease.sh#L315) sends a generic cleanup command. The [MCP claim handler](../../../apps/web/lib/mcp/packs/nonprod-lease-pack.ts#L364) forwards it and the [lease create path](../../../apps/web/lib/nonprod/environment-lease.ts#L380) persists it. No stripping stage was found. This makes the real launcher incompatible with the exact owner predicate, which requires a null cleanup command. Do not weaken that predicate. Omit the cleanup command from new Contributor preview launcher claims. Do not weaken the predicate or rewrite historical rows. The correction enables both terminal container fencing after positive owner proof and routine owner release of a process-free lease without approval under BI-31AC1F90 OBJ-PC-1. Run real launcher-shape fence cases: terminal stops the owned container, active holds it. Existing owned-runtime teardown remains responsible for stopping the old preview. The obsolete release-envelope settlement path in obsolete-lease-envelope.ts also requires a null cleanup command, but independently requires slotManifestVersion 1. Real active-candidate launcher claims persist no slot manifest, so omitting the command alone does not enable that path. An actual launcher-shaped fixture must hold its envelope. Do not weaken that settled-without-resources predicate. The path only closes obsolete requests and never invokes release or grants authority.

For convergence, a running legacy preview remains on its existing command-bearing row and cannot attest. It must end through its existing authorized release/teardown path or ordinary expiry before the operator explicitly starts a fresh attempt. Do not auto-claim or retrofit a live row. Same-key replay returns the old row, even terminal, so use the launcher's existing `DPF_DEV_PORTAL_CLAIM_KEY` override to assign a new unique attempt key for the explicitly requested restart. Reject any override beginning with gate: or outside the dev-portal: namespace before the claim call. Keep the explicit attempt key stable across retries and resume for that attempt. The launcher must surface that a terminal same-key result requires an explicit new attempt.

Retry launcher release only on a structured `data.retryable === true` result carrying the release contention code, with at most two retries after the first attempt, short bounded backoff and the exact same lease and session. Stop immediately on other refusal or malformed response, and report exhaustion without creating a replacement lease.

## Review item 8 — MCP release contention

The release wrapper in `nonprod-lease-pack.ts` must preserve `nonprod_release_wait_settlement_contended` as a typed error with `data.retryable: true`. It must not report the rolled-back attempt as a final failure or use the generic do-not-retry message. Other release errors retain their existing classification. The retry remains caller-driven and release is idempotent.

## Research

The pin sources and downstream sequencing are in the [S5 provisioner design](2026-11-25-s5-rehearsal-draft-provisioner-design.md). The existing sanitized-clone probe reads network endpoint and database name, which cannot distinguish two clusters behind the same endpoint at different times. PostgreSQL documents the stronger available fields in [control file functions](https://www.postgresql.org/docs/16/functions-info.html) and [the shared database catalog](https://www.postgresql.org/docs/16/catalog-pg-database.html). PostgreSQL 16 does not revoke public execute on this function in its [initdb ACL script](https://raw.githubusercontent.com/postgres/postgres/REL_16_STABLE/src/backend/catalog/system_functions.sql). The preview uses its existing bootstrap superuser, not a new database role. Verify actual privileges and the probe in disposable PostgreSQL.
