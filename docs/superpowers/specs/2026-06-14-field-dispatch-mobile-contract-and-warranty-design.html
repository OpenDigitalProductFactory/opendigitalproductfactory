1. Purpose

The dispatcher is only as good as its field signals and its field actions. In production those originate on the technician's mobile app: GPS location, routing, the customer/site detail the tech needs on arrival, the field-captured invoice, and the door payment. The operator named the full surface — "geo-location, communication, routing and customer/location details… formulate an invoice with field input easily… collect payments… warranty service aspects." This spec turns that into a typed contract the mobile thread implements and the dispatcher consumes, and it adds the one genuinely new domain nuance: warranty-aware service.

2. The mobile field-app contract

Six surfaces. Each is something the mobile app provides and the dispatch runtime consumes.

Geo-locationtechnician position, departure/arrival (geofence), live ETA — to fire on-my-way and detect running-lateMobileFieldSignal stream (location | departed | arrived | eta) — already the harness contract

Surfaces 1–3 are the routing/communication loop the harness already simulates via MobileFieldSignal + the geo-temporal model. Surfaces 4–6 (detail, invoice, payment) are the on-site action loop. The customer-facing channel reality still applies: the platform comms layer has WhatsApp/email/in-app but no SMS/voice yet (field-dispatch deferred-decision #6) — the mobile app may itself become a customer-reachable channel.

3. Warranty-aware service (the field-service nuance)

Installed equipment carries warranty terms that differ by component and by coverage type. The canonical example: an AC compressor commonly has a 10-year parts warranty but no labor coverage. A compressor failure in year 7 means the part is free to the customer (the contractor may reclaim its cost from the manufacturer separately) while the labor is billed. The dispatcher and the field tech need this at quote/invoice time, and the field invoice must classify each line as covered vs. billable.

Built & verified in @dpf/validators/field-dispatch-warranty.ts:

  • assessWarranty(equipment, component, atDate) → parts/labor coverage from install date + per-component terms.
  • classifyServiceLines(equipment, lines, atDate) → each invoice line marked covered (billed $0) or billable, with a reason.
  • The compressor case proves out: a $1,400 compressor part bills $0 in year 7; the $520 labor bills; an unknown component bills.

Warranty data lives on the equipment record (a CustomerConfigurationItem HVAC sidecar per the capability spec) — install date + per-component {partsWarrantyMonths, laborWarrantyMonths, source}. The classified lines feed the DPF invoice (F12) and the mobile field-invoice surface shows the tech what is covered. A manufacturer-warranty claim (the contractor reclaiming the part cost) is a distinct downstream flow, not the customer invoice.

4. SysML model

package FieldDispatchMobileContract {

  requirement def RM1_GeoLocation        { doc /* mobile emits position, departed/arrived (geofence), ETA */ }
  requirement def RM2_CustomerComms       { doc /* mobile surfaces/triggers confirm/on-my-way/running-late/complete + delivery state */ }
  requirement def RM3_RoutingNavigation   { doc /* mobile provides navigation + reports ETA to the next site */ }
  requirement def RM4_CustomerLocationDetail { doc /* mobile shows customer, site/access, on-site equipment, service history */ }
  requirement def RM5_FieldInvoice        { doc /* mobile captures labor+parts -> warranty-classified draft invoice (-> QuickBooks) */ }
  requirement def RM6_PaymentCollection   { doc /* mobile collects payment at the door against the invoice */ }
  requirement def RW1_WarrantyAwareService{ doc /* per-component parts/labor coverage from install+failure date drives invoice line classification */ }

  port def MobileFieldDevicePort  { // MobileFieldSignal: location|departed|arrived|eta|status (harness §6.5) }
  port def CustomerContextPort   { // read: customer, site/access, equipment record + warranty, service history }
  port def FieldInvoicePort      { // capture ServiceLine[] -> classifyServiceLines -> draft DPF Invoice (F12) }
  port def PaymentPort           { // collect payment (link / tap-to-pay) -> record against invoice }
  port def WarrantyPort          { // assessWarranty / classifyServiceLines over the equipment record }

  part def MobileFieldApp {
    // the native archetype app (separate thread, PR #1886) IMPLEMENTS these ports
    port device   : MobileFieldDevicePort;
    port context  : CustomerContextPort;
    port invoice  : FieldInvoicePort;
    port payment  : PaymentPort;
  }
  part def EquipmentRecord { // CustomerConfigurationItem + warranty sidecar: installDate + per-component terms }
  part def WarrantyPolicy  { port warranty : WarrantyPort; ref part equipment : EquipmentRecord; }

  allocation m1 allocate MobileFieldApp        to nativeArchetypeApps;            // other thread (#1886)
  allocation m2 allocate WarrantyPort          to validators.fieldDispatchWarranty; // built + verified
  allocation m3 allocate FieldInvoicePort      to fieldDispatch.F12_quickbooksInvoice;
  allocation m4 allocate MobileFieldDevicePort to harness.mobileSignals;          // convergence schema

  satisfy RM1 by MobileFieldDevicePort;  satisfy RM4 by CustomerContextPort;
  satisfy RM5 by FieldInvoicePort;       satisfy RM6 by PaymentPort;
  satisfy RW1 by WarrantyPolicy;

  verification case def VC_Warranty {
    subject e : EquipmentRecord;
    objective /* compressor 10yr-parts/0-labor: part covered + labor billed in yr 7;
                 classifyServiceLines bills the right total (35/35 validators tests) */
  }
  verification case def VC_SignalParity {
    objective /* the mobile device port emits the MobileFieldSignal schema the harness asserts */
  }
  verify RW1 by VC_Warranty;  verify RM1 by VC_SignalParity;
}

5. Convergence with the mobile thread

The native mobile archetype apps thread owns the app and its spec. This document is the dispatch-side contract it converges on:

  • The app implements MobileFieldDevicePort (emitting the MobileFieldSignal schema the harness already verifies), CustomerContextPort, FieldInvoicePort, and PaymentPort.
  • The dispatcher consumes those signals/actions and proposes notifications, assignments, and invoices.
  • Warranty classification is shared logic (@dpf/validators/field-dispatch-warranty) — the mobile field-invoice surface and the back-office invoice both call it, so a covered part is $0 everywhere.

Recommended handoff: the mobile spec adds a "Field Dispatch contract" reference to this document and its port list, rather than re-specifying the signal/invoice/warranty shapes. That keeps one source of truth for the seam and avoids the two threads drifting. (Filed as a cross-thread note, not a direct edit to the mobile spec.)
