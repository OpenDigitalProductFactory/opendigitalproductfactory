Multi-Business "Town" Super-App — Mobile

BIto file under EP-MOBILE-ARCHETYPE
Statusdraft — for operator review
Date2026-06-14
Extends2026-06-14-native-mobile-archetype-apps-design

One resident's app that holds many local businesses as "spaces" — book the auto shop, join the hairdresser's waitlist before you arrive, check equipment availability and reserve it at the rental shop — each business in its own space, your persona there (customer or employee) driving the UI, and one device-level setup for payments, location, and notifications reused across all of them. The town, in one app.

1 · The vision, and the one insight that makes it tractable

The previous spec built "one generic app connects to one self-hosted business install." This evolves it to "one app engages with many businesses." The precedents are well-trodden — Uber's personal/business profiles (one account, switchable profile, a different payment method per profile), Slack/Mastodon multi-workspace (N independent backends, one client, a switcher, notifications aggregated), and WeChat/Gojek super-apps (many independent merchants, one shared wallet + discovery + identity).

The insight: this is a client-side generalization, not server multi-tenancy. Each business stays a separate single-org-per-install backend — unchanged. The app simply holds a list of install-connections ("spaces") instead of one, plus a shared device layer and two consciously-thin federation services. Single-org-per-install — the load-bearing DPF law — is fully preserved. Research confirms the booking / rental / waitlist / invoice / payment models already exist and are storefrontId-scoped, so the server needs almost no change; the work is the multi-space client + customer surfaces + two thin services.

3 · The three layers

① Spaces (client)

A Space[] registry generalizing today's single serverConfig. Each space = { url, descriptor, session, manifest }. A switcher (Slack rail / Mastodon corner / WeChat tray) + a "my town" home. Entering a space loads its persona-driven UI and re-themes. All the heavy lifting.

② Shared device (client)

One device wallet (Apple/Google Pay + saved card), one location grant, one push token — granted once, reused by every space. Each business charges via its own processor; the device just presents the instrument. (Uber-profiles + Gojek shared-platform.)

③ Federation (2 thin services)

The directory ("Nearby" businesses → install URL) and an optional identity broker (sign in once, present a scoped token to each install). The only two centralization points — every super-app centralizes exactly these and federates everything else.

4 · Identity — the crux, answered honestly

This is the one genuinely hard problem, and no precedent decentralizes it. Slack/Mastodon keep identity siloed per backend — "portability" is the illusion of one client holding many separate logins. WeChat/Gojek achieve real portability only because a central host issues scoped tokens. Portable identity over truly independent installs requires some shared trust anchor; the only question is how thin.

Security-sensitive (touches every /api/v1 route's principal assumptions) → build carefully with a live customer-login check.

5 · Payments — device wallet, each business its own processor

Confirmed standard (Stripe Connect, Apple/Google Pay): the client holds the instrument once; each business charges via its OWN processor account (its own Stripe/Square) — each business is its own merchant of record. This is exactly DPF's conduit, not broker stance: the platform records Invoice/Payment but never holds everyone's card. The Uber "business vs personal card" = a payment context per space (and optionally a personal/business sub-context within a space). Card-on-file for repeat business is vaulted at that business's processor (Fresha/Housecall pattern), never centrally.

Store policy is a tailwind, not a blocker: physical goods + real-world services are exempt from in-app purchase on both stores (Apple guideline 3.1.3(e); Google Play Payments policy) — haircuts, auto service, equipment rental all qualify, with no store commission. Keep any purely-digital in-app SKU out of this path (those still require store billing).

6 · Geo + notifications — one grant, fanned per space

  • Location: one device permission (expo-location), reused by every space — powers the directory's "Nearby," waitlist proximity ("I'm 5 min away"), and field geo. A business only sees location scoped to an active interaction, never ambient cross-business tracking.
  • Push: one device token, registered with each space's /api/v1/notifications/register-device (one device, N registrations). Payloads carry a spaceId so a tap routes to the right space. Notifications aggregate into one inbox, badged per business (Slack's all-workspaces model). The Expo push sender adapter (built, gated by DPF_PUSH_ENABLED) delivers per space.

7 · The directory — "Nearby," the second thin service

A discovery directory turns a pile of independent installs into a browsable town. Mirror WeChat: a geo "Nearby" list + search + a recently-used tray, with QR / deep-link as the offline→app "join this business" bridge. It is a thin registry indexing participating installs — name, location, archetype, install URL — keyed by each install's existing public /.well-known/dpf-instance.json descriptor. It holds no business data; it is a phonebook, the second (and last) consciously-centralized service. Opt-in for both businesses (list me) and residents (find me).

9 · What's client vs server vs federation

Server — ~unchanged

Each business = its own single-org install. Booking / rental / waitlist / invoice / payment models exist + are scoped. Only additions: per-space customer auth + the customer-facing read/booking endpoints (requireCustomerAuth) + per-business processor wiring + the push sender (built).

Client — the big work

Space[] registry + per-space sessions/manifests + switcher + "my town" home + the shared device layer (wallet, geo, push fan-out) + the customer use-case screens (waitlist/booking/rental).

Federation — 2 thin services

The directory (Nearby) and the optional identity broker. New, small, opt-in, Arcamanus-hostable. Hold no business data. The only centralization.

10 · Research & benchmarking (cited)

  • Two-sided, mode-by-profile — Uber personal/business profiles (one account, switchable profile, payment-method-per-profile, defaults to last-used) is the direct precedent for per-space context. Lyft proves a single app with a role toggle is viable; Uber/DoorDash split the heavy workforce role into a second binary. We adopt the per-space toggle.
  • Super-apps — WeChat mini-programs (host owns identity+wallet; merchants own their space; scoped token, never a password) + Gojek/Grab (one onboarding, shared wallet, strong central governance of payments/identity/data while services innovate independently). Discovery = search + geo "Nearby" (~5 km) + recently-used tray + QR.
  • Multi-account clients (closest UX) — Slack workspaces (N independent backends, switcher rail, per-workspace identity, notifications aggregated, no cross-workspace identity bleed) + Mastodon multi-server (corner switcher across independent instances). This is our "spaces" model.
  • Local-commerce — Fresha + Booksy (one consumer identity + saved card reused across independent businesses; availability/booking/waitlist). Field-service (Housecall Pro) is still business-by-business — validating "the town in one app" as new ground there.
  • Payments — Stripe Connect (store the instrument on the platform, charge on each connected account; each is its own merchant of record) + Apple Pay tokenization (device holds the card; each merchant's processor charges; merchant tokens are per-business). Store policy: Apple 3.1.3(e) + Google Play exempt physical/real-world services from IAP.

11 · SysML v2 architecture substrate

package MultiBusinessTownApp {

  // ---- Systems ----
  part def TownApp;            // one generic binary (Arcamanus LLC)
  part def BusinessInstall;     // a single-org-per-install backend (unchanged)
  part def DeviceLayer;         // wallet + geo grant + push token (shared)
  part def Directory;           // thin registry: Nearby businesses -> install URL
  part def IdentityBroker;      // optional thin scoped-token issuer

  // ---- A space = one joined business connection ----
  part def Space {
    attribute instanceUrl : String;
    attribute descriptor  : InstanceDescriptor;   // /.well-known/dpf-instance
    attribute session     : SpaceSession;         // per-space tokens
    attribute manifest    : AppConfigManifest;     // per-space persona/theme/caps
  }
  part app : TownApp { part spaces : Space[0..*]; part device : DeviceLayer; }

  // ---- Requirements ----
  requirement def R1_FederatedMemberships { doc /* each business is an independent install; identity/session per space, no bleed */ }
  requirement def R2_NoServerMultitenancy  { doc /* single-org-per-install preserved; multi-business is client-side */ }
  requirement def R3_PersonaPerSpace        { doc /* the install manifest drives customer|employee per business */ }
  requirement def R4_DeviceCustodiedPayments { doc /* device holds instrument; each business charges via its own processor */ }
  requirement def R5_OneGrantManySpaces      { doc /* geo + push granted once, reused; push token N-registered, payloads carry spaceId */ }
  requirement def R6_ThinFederation          { doc /* directory + optional identity broker hold no business data; opt-in */ }

  // ---- Allocations: obligation -> substrate ----
  allocate R1_FederatedMemberships to serverConfig_to_spaces, auth_store_per_space, SecureStorage_per_space;
  allocate R2_NoServerMultitenancy  to BusinessInstall, storefrontId_scoping;
  allocate R3_PersonaPerSpace        to appConfig_per_space, manifest_persona;
  allocate R4_DeviceCustodiedPayments to DeviceLayer_wallet, Invoice_Payment_models, per_business_processor;
  allocate R5_OneGrantManySpaces      to expo_location, PushDeviceRegistration_per_install, spaceId_in_payload;
  allocate R6_ThinFederation          to Directory, IdentityBroker, wellknown_dpf_instance;

  // ---- Verification ----
  verification def V_Spaces  { doc /* unit: Space[] registry add/switch/remove + per-space session routing */ }
  verification def V_NoBleed { doc /* a space's tokens/manifest never resolve for another space */ }
  verification def V_Persona { doc /* live: same device, two installs, two personas */ }
  verify R1_FederatedMemberships by V_Spaces, V_NoBleed;
  verify R3_PersonaPerSpace by V_Persona;
}

13 · Decisions for you

A · Identity

Rec: per-space memberships now; broker later

Ship Slack-style per-space logins (fits single-org-per-install); add the thin identity broker (sign-in-once) only when the "one identity, many businesses" UX is worth the trust anchor.

B · Directory host

Rec: Arcamanus-hosted, opt-in

The registry needs a host (every super-app centralizes it). Arcamanus LLC hosting a thin, opt-in "Nearby" index is the natural fit — it holds only public descriptors, no business data.

C · Payments

Rec: device wallet + per-business processor

No central broker (cohesion with "conduit not broker"). Confirm each business brings its own Stripe/Square; the device holds the instrument.

D · Scope first

Rec: single-business UX first, multi-space-ready

You said "you don't need to" go multi-business — so M1 ships the spaces foundation but the app is fully usable with one space; the "town" lights up as businesses join.

14 · Out of scope & relation to existing work

  • No server multi-tenancy — each business stays its own install; this is the load-bearing constraint.
  • No central money broker — payments stay conduit-not-broker; each business is its own merchant of record.
