Workstream

Harness — make the local Qwen path survive a long session

DPF runs its local generation model on Docker Model Runner at localhost:12434 (qwen3-coder when this was written; qwen3.8-27b since). The dsh teardown said the thing that kills a small local model isn't the model — it's unmeasured context. Correction (2026-08-22): that failure is not wired into this repo — the served-context path below was already built and running. See the corrections on each item.

The local endpoint has no context window, so the capacity gate never applies to it Code reading verified Diagnosis previously rejected — BI-9DFAFB4A Premise falsified — verified live 2026-08-22

metadata-extractor.ts:86 sets maxContextTokens: null for Ollama with the comment "Ollama doesn't report this in /api/tags." task-router.ts:154 then gates on endpoint.maxContextTokens !== null && … < minContextTokens. A null capacity doesn't fail the check — it skips it. The local model is the one endpoint whose real window is smallest and the only one exempt from the size gate.

Correction (2026-08-18, on merge). The code reading above is accurate, but the conclusion that it is a live defect is not. BI-9DFAFB4A investigated this exact asymmetry in July 2026 and rejected it as the core defect: the pipeline-v2 Stage-5b tier sort already ranks user_configured ahead of bundled, so the local endpoint only wins when every paid endpoint was excluded by a hard constraint. In that case the null-capacity exemption is a deliberate last-resort safety net — gating it closed would fail the request outright instead of degrading. The shippable part of that BI was banner honesty, and it shipped: routed-inference.ts:700 carries the BI-9DFAFB4A rationale in-tree today. Treat this section as a re-derivation of settled analysis, not a new finding.

Second correction (2026-08-22, live sweep). The code reading is accurate about the two files it cites, but neither is load-bearing, so the premise is wrong twice over. First, extractModelMetadata — and with it extractOllama and its null — has no production caller: the only references in the tree are the index.ts re-export and its own test file. It populates nothing. Second, the endpoint's maxContextTokens is not null in practice; it is written from the true served context by a reconcile that already ships (see the struck next step below). The divergence between the two gate forms is likewise not live-versus-live: pipeline.ts:172 sits in getExclusionReason, and getExclusionReason, filterHard, and routeEndpoint have no production callers — pipeline-v2 imports only filterByPolicy from that module. The live check is pipeline-v2.ts:158, which uses the same fails-open !== null form as task-router.ts:154. The live paths agree; the fails-closed variant is dead code.

Next steps

  1. Give the local endpoint a real served-context number — already shipped

    Withdrawn 2026-08-22: this was built before the analysis was written. The claim that "nothing in the repo queries /engines/_configure" came from a grep that filtered out not_configured/user_configured and discarded the real hits along with them.

    The loop is closed end-to-end on main: getServedContextTokens/setServedContextTokens in dmr-runtime-config.ts read and write DMR's /engines/_configure; reconcileLocalModelContext runs at boot and on a 20-minute interval from instrumentation.ts, reads the true served context (explicitly not /v1/models, whose card default it calls out as misleading), writes ModelProfile.maxContextTokens for providerId in ("local","ollama"), and self-heals the column when re-profiling drifts it; loader.ts:218 then feeds it to endpoint.maxContextTokens. Verified live 2026-08-22: DMR reports context-size: 131072 for the installed generation model and the matching ModelProfile row holds 131072.

    The reusable lesson is the grep, not the router: an exclusion pattern chosen to suppress noise (not_configured, user_configured) silently suppressed every true positive, and the resulting absence claim read as verified substrate. An absence claim needs the unfiltered hit count before it is recorded.

  2. Make a null capacity fail closed, not open — withdrawn

    Withdrawn on merge. BI-9DFAFB4A already considered and rejected this change: because Stage 5b only reaches the local endpoint after every paid endpoint has been hard-excluded, failing closed on unknown capacity would turn a degraded answer into no answer at all. The null exemption is load-bearing, not an oversight. The recommendation immediately above — populate a real served-context number for the DMR endpoint — would have removed the ambiguity on its own, and has since turned out to be already shipped (see its withdrawal note).

    The prior analysis is in-tree; re-deriving it cost a round trip, which is the reusable lesson.

  3. Decide whether context pressure belongs in the loop at all

    Run this through dpf-brainstorming → dpf-decision-via-kernel rather than assuming. Three genuinely distinct options: (a) proactive compaction on the dsh model, (b) fresh-context-per-round on the Ralph model — likely a better fit given Build Studio already has discrete phases, (c) leave it reactive and just make the failure legible. Option (b) deserves real weight; a 30B model does better re-deriving state from the workspace than compacting a degrading transcript.

    This is an architecture decision with a kernel-scoreable shape, not an implementation detail.

  4. If compaction wins, route the summarizer to a stronger model than the conversation

    dsh exposes this as summarizationProvider/summarizationModel for exactly this reason. A bad checkpoint poisons every turn after it, so this is the highest-leverage single knob for a weak local model. DPF's quality-tiers and task-requirements already have the vocabulary to express it.

    Costs a little cloud spend on a rare call; protects the whole session.

  5. Do not trust a 4-chars-per-token estimator if you build one

    dsh's meter is unconfigurable and its own docs admit "CJK text and JSON schemas underprice badly at four characters per token." Tool schemas are JSON, so this is wrong for every agent session, not just non-English ones. Anchor on provider-reported usage where available and estimate only the delta.

    The single most-reported dsh defect. Free to avoid; expensive to retrofit.

First move

Steps 1 and 2 are a small, self-contained, testable change with a clear failing-test shape — a good dpf-tdd candidate and worth filing as one BI before any of the architecture work starts.

Workstream

Router — stop the interface silently choosing the model

I was wrong earlier to imply DPF needed to learn multi-model abstraction from T3. It has more of it than either comparison point, and in a direction neither has.

Correction — DPF's router is more governed than pi-ai's Verified

Adapter registry with per-provider adapters for Anthropic, Gemini, Ollama, OpenAI, OpenRouter, Codex CLI and a generic CLI pool; capability probes and a profile cache; cost ranking; quality tiers; champion/challenger; capacity-based routing exclusion; a provider-suitability compiler with its own runtime policy and telemetry. pi-ai gives you a model catalog. DPF has a governed selection layer, which is the harder half and the part that matters for a regulated small business.

apps/web/lib/routing/ — 60+ modules incl. adapter-registry, capability-probes, cost-ranking, quality-tiers, champion-challenger, provider-suitability/

The T3 lesson that does apply: interface quality silently overrides model quality External

The single most useful line in the T3 transcript: "I ended up finding myself defaulting to OpenAI models even in things they were worse at because I just liked having a good app." A domain expert knowingly chose a worse tool because the surface around it was more legible. DPF operators will make that trade constantly and never notice they made it — and DPF has no instrument that would detect it.

Two config surfaces can disagree, and a third exists to flag it Verified

/platform/ai/providers governs routing for ideate/plan/review; /platform/ai/build-studio governs build-phase dispatch. Your own skill calls the mismatch "the classic 'I set local but it called cloud' confusion," and /platform/ai/runtime-health exists to surface it. A reconciliation view is a patch over split authority — it's the config-surface form of "which tmux pane was which."

Next steps

  1. Instrument the adoption-vs-quality gap

    You already write adapter telemetry and skill telemetry. Join them: for each task type, compare the model the router recommended against what actually ran and what the operator chose when given the option. A persistent divergence is the T3 distortion showing up in your own data.

    Turns an anecdote into a metric. Cheap — the telemetry writers exist.

  2. Name the winner and the reason in operator language, at the point of use

    task-requirements.ts already carries a selectionRationale per task type ("Low-risk summarization — cheap/local utility tier"). That string is doing nothing for the person watching a build. Surface it: "Drafting your reply — using the fast local model because this is low-risk."

    The cheapest legibility win available. The content already exists and is already written for humans.

  3. Collapse the two config surfaces, or make one authoritative

    Don't add a fourth reconciliation view. Either build-studio dispatch reads from providers-and-routing with a documented override, or the split is made explicit in the UI so nobody can set one believing they set both. Route via dpf-architecture-review — this is a canonical-contract question.

    Every reconciliation surface you add is an admission that state is split. Fix the split.

  4. Treat subsidised-subscription execution as a strategic question, not a feature

    T3's actual moat is running Claude Code and Codex through official SDKs against the operator's own subscription — "8 to 14 grand for 200 bucks" — negotiated with the labs rather than hacked. DPF already has codex-cli-adapter and a CLI pool, so the substrate exists. What's unresolved is whether a small-business install can lean on customer-held subscriptions, and what happens when a lab changes policy — which the transcript notes has already been threatened once and held.

    Unit-economics decision with a real external dependency. Belongs in front of the founder, not in a sprint.

Workstream

Cockpit — fleet legibility for non-technical operators

The T3 argument isn't about terminals. It's about supervising N concurrent, long-running, semi-autonomous workers whose state is invisible unless you go looking. That's Build Studio. And your operators can't build their way out the way a founder-programmer can.

Correction — an owner-facing status vocabulary already exists Verified

My earlier "no fleet view" read was too shallow. BuildOperatorOverview carries an eight-state ownerState enum — working, waiting-capacity, waiting-owner, blocked, inconclusive, failed, complete, not-started — with semantic colour per state, backed by customer-status-projection and an ownerSafeBuildText sanitiser. Two of those states name who is blocking, which is precisely the distinction an owner needs. This is a strong asset.

I found no single view answering that across builds and coworkers — components/cockpit/ holds one file (GraduationVetoButton.tsx) and /admin/cockpit is an events table. That's a narrow sweep, not a product-wide audit.

SKILL.md §B5

The three properties to design against

The wrong takeaway from T3 is "build more UI" — the transcript itself criticises two bad GUIs. The argument is really about three properties, and a GUI is only one way to deliver them. Test any Build Studio surface against these rather than against "is it graphical."

PropertyThe testWhere DPF stands
State legibility The operator reads what's happening and never has to recall it. Recall fails discontinuously at ~5 items. Strong per build (ownerState). Unproven across builds.
Work durability Close the laptop; the work continues. The deliverable is "I stopped thinking about it." Server-side builds suggest this holds — but self-upgrade is documented to strand in-flight builds.
Cheap re-entry Away four hours. What do you see on return — a summary of what changed and what needs you, or a wall of activity rows to reconstruct? BuildChangeSummaryBand and BuildDecisionLedgerBand exist. Whether they answer "what happened while I was gone" is untested.

Next steps

  1. Build one cross-build attention view on the existing projection

    Not a new dashboard — a list of every in-flight build and coworker with its ownerState, sorted so waiting-owner and blocked float to the top. The projection layer already produces every value this needs; nothing new has to be modelled. Answer one question: what needs me right now.

    Highest-value UX item on this page, and it is assembly, not invention.

  2. Run the re-entry test with a real non-technical operator

    Start three builds, walk away four hours, come back, and record what they can and can't answer without opening the database. Use dpf-verify-on-live-install for the preflight so the run is on a provable runtime. Findings become BIs.

    Cheap, and it will produce better next steps than any amount of further reading.

  3. Treat "truth lives in four places" as an owner-facing defect, not an ops note

    Where the UI can't answer a question an operator legitimately has, that's a gap in the surface, not a reason to document the psql query. Pick the top three questions the skill currently answers via database or docker logs — which model ran this, why did this stall, what did the tool actually return — and give each an owner-safe surface.

    This is where the DPF version of "ask Claude Code to find my Claude Code session" lives.

  4. Write down the WIP cap rationale, then treat 3 as a UX constant

    If the cap ever rises above five for capacity reasons, the attention view in step 1 stops being a convenience and becomes load-bearing. Record the cognitive-load rationale next to the capacity one so the tradeoff is explicit.

    One paragraph now; prevents a silent regression later.

  5. Extend dpf-ux-fit-review with a fleet-legibility check

    The skill already triggers on dashboards, status, cards and empty states. Add the three properties above as explicit review questions so every future UI-impacting change gets tested against cognitive load rather than only against visual fit.

    Makes this analysis durable instead of a document someone read once.

First move

Step 2 before step 1. Four hours of observation will tell you what the attention view must contain; building it first means guessing.
