Research · October 12, 2026

A consolidated routing, evaluation and troubleshooting tool

Recommendation: retain DPF’s evidence and governance model; refactor the default experience into one focused explorer and one contextual inspector.

Refined management flow

Traffic, Evaluation and Providers share one task/data/time/provider scope bar. Catalog management and operational evidence retain the same context; browser history and reload restore the chosen page, provider and filters through a validated URL fragment. Provider details have a compact breadcrumb and direct traffic/evaluation actions. Recent request evidence is capped at three rows with full investigation in an overlay; design and policy stay behind contextual disclosure.

Refactoring removes the separate scope copy and duplicated provider-list renderer, reuses provider details in both overlay and setup views, and centralizes navigation/scope restoration. These presentation improvements preserve the existing configuration authority and read projections.

Consolidated navigation and configuration ownership

Providers & Routing remains the canonical provider configuration home. Provider and model inspectors link to its existing routing, account and clearance controls; provider setup links back to scoped traffic and task outcomes. Task, classification and time context survives both directions. Coworker model pins stay in the existing assignment settings. The operational projection consumes their effects rather than inventing another override store or independently writable form.

The initial standalone route-choice prototype has been replaced by contextual navigation to provider setup. The sensitive-work form now previews the established ProviderClearanceOverridePanel contract: selected sensitivity classes, rationale, risk acknowledgement, future expiry, audit and revoke. This is local demonstration data only; production integration must reuse the existing actions and permissions.

User-selected routing overrides

Users may deliberately choose a lower-ranked or reduced-capability route after reviewing its warnings. The choice carries a task/data scope, connected model/account/channel, reason, expiry and risk acknowledgement. Missing capability stays visible rather than being silently treated as present. A data boundary exception follows the existing authorization/policy process, and payment, capacity, cooldown or operator-pause holds retain their normal release conditions. Outcome comparisons must retain the override marker so tuning evidence can distinguish default routing from deliberate user choices.

Refinement: task outcomes, sensitivity and overlays

The revised prototype groups assignments and providers in the default graph. Provider overlays expose their model catalogs, account/channel boundaries, capability floors and current fixture availability. Request overlays bring decisions, attempts/holds, costs, feedback and evidence into one place without scrolling the page to a separate inspector.

Evaluate tasks compares completion, task-quality evidence, median elapsed time and attributed costs for one task family and rubric. It preserves unknowns and denominators. Operator assessments remain separate from evaluator results and cannot apply a routing promotion. Design conformance remains a separate technical disclosure.

Success, error, automatic stop, operator pause and unknown evidence are distinct. Context/token budgets, payment, quota/cooldown, disabled configuration, and exhausted immutable review packets each need their own recovery owner and release condition.

The source activity outcome DTO already carries task/model/provider, harness identity, confidence, token total, cost, success signal, quality signal, evaluator source and evidence strength. Use these existing projections for consolidation. Current catalog and capacity states must not be projected backwards onto a historical routing decision.

Scalability: show stable assignment/provider groups, then search and drill into catalog rows; aggregate edges by scope rather than rendering every event. Preserve a compact recent-evidence strip and the full evidence list in an overlay. Later implementation needs pagination or virtualization for large catalogs and evidence lists, permission-scoped reads and preserved deep links.

Agent use: the graphical view and assistant should read the same permission-scoped projection, with identical task, time, classification, account and cohort filters. Share safe receipt references and scoped deep links, so an assistant can inspect the cause behind a visual signal and verify the effect of a tuning change from structured evidence. Screenshots are a useful explanation, not diagnostic authority.

Model names, exposures, sample accounts, classification rules, costs and evaluator outcomes are illustrative, not live measurements or provider recommendations. Feedback stays in memory until reload. The prototype does not alter any operational holds or platform settings.

What DPF’s own experience tells us

  • Useful foundations already exist: Designed / Observed / Compare, shared replay, routing filters, evidence tables and architecture drill-through.
  • Live inspection: the map appears below a large architecture band and numerous topology controls. Provider labels clip at the right edge; coworker interactions and provider routes compete in the same canvas.
  • The existing owner-first plan already diagnosed repetition: its August audit recorded 563 visible words, 52 controls, duplicate activity presentations and an over-wide activity rail. Those are historical measurements, not measurements of today’s page.
  • Freshness matters: during this review the page’s initial snapshot changed from 40 to 400 decisions after refresh. A selected request should remain pinned while aggregate data refreshes, with an explicit freshness label.

The progressive disclosure contract

  1. Overview: actual request counts by workload and model, scoped to one window. Stable geometry; no animated decorative traffic.
  2. Selection: emphasize the connected paths; show the outcome and routing explanation in one inspector. Unrelated paths recede.
  3. Request: show ordered attempts, eligibility, failures, fallback and final outcome. “Fallback configured” and “fallback occurred” are distinct.
  4. Technical detail: disclose safe receipt IDs, correlation, design revision, source versions, topology and replay. Missing evidence remains unknown.

What makes it robust

  • Consistent time window and stable request selection across graph, list, inspector and replay.
  • Distinguish not observed, not configured, excluded, temporarily unavailable, denied and evidence unavailable.
  • Aggregate by stable workload / model / endpoint keys rather than render an edge per event. Preserve counts and safe drill-through.
  • Trace every fallback against the original policy and capability obligations. A healthy provider is not automatically an eligible model.
  • Label denominators, units and freshness. Do not imply total requests when correlation coverage is incomplete.
  • Keep meaningful model labels visible, with provider / adapter identity underneath. Preserve list access for keyboard and small-screen use.
  • Configuration edits and coworker dispatch stay behind their existing governed action boundaries. Map selection only inspects.

Architecture & refactoring allocation

Canonical route: /platform/ai/operations-map. Reuse RoutingArchitectureOverview, OperationsTopologyCanvas, ActivityRoutingWorkbench, the routing comparison view model and existing evidence ledgers.

For later implementation, allocate 80% of effort to refactoring and usability simplification, with 20% for necessary additions. This explicit operator direction supersedes the earlier 20% refactoring allocation. Refactoring priorities: consolidate scope / replay / selection state, extract one pure aggregate projection, reuse one inspector, and retire duplicate presentations. No new routing engine, telemetry ledger, schema or graph library is proposed.

Source truth remains RouteDecisionLog for selection and exclusions, RouteOutcome for dispatch outcomes, AdapterRunTelemetry for adapter evidence, and canonical registries for designed routes. Join only with established correlation keys. Model-level labels must come from authoritative identity, not guesses from a provider name.

UX fit: fits with guardrails.

Owner: Platform. Persona: operator diagnosing AI work. Local controls only. Keep the five canonical governance stations inside the routing inspector; the simplified middle node is a visual summary, not a replacement policy. Preserve permissions, technical deep links and replay parity. Measure served-route UX budgets, accessibility and both themes before any implementation handoff.
